# 记录中心游泳记录联动修复任务清单

更新时间：2026-08-02

本文用于承接“个人活动记录里有公开水域和泳池游泳数据，但记录中心没有相应记录”的根因治理。任务目标不是补一个 10K 或某次活动的特例，而是让泳池游泳、公开水域游泳在记录中心、当前最佳、刷新纪录、时间轴里共享同一套可重建事实链路。

Task Loop 前置文档：

- 开发交付手册：`docs/运动生涯记录中心V2（多运动纪录）开发交付手册.md`
- 专项契约摘要：`docs/记录中心游泳记录联动契约摘要.md`

## 当前结论

这次修复可以作为一个总任务执行，但必须拆成有顺序门禁的子任务。

统一主线保持不变：

```text
Activity -> Record Metric Result -> Current Best / Record Progression -> Timeline Event / Records Center ViewModel
```

修复必须覆盖：

- 泳池游泳标准距离记录。
- 公开水域标准距离记录。
- 公开水域最长距离、最长历时等整次活动类记录。
- 当前最佳和刷新纪录的时间轴里程碑。
- 活动新增、变更、删除后的记录生命周期联动。
- 前端记录中心缓存刷新。

## 当前根因

### 1. 泳池游泳缺少可证明的池长事实

当前默认库中存在泳池游泳活动，且部分活动有 `laps_json` / lengths 数据，但活动表和 lap payload 中没有可用的 `pool_length_m` / `pool_length` 事实。泳池标准距离 best effort 依赖真实池长和 lengths/laps，缺失池长时当前 resolver 返回 `pool_length_missing`，不会生成正式 metric result。

治理原则：

- 不从总距离 / lap 数倒推池长。
- 不在前端补算池长。
- 只从 FIT / provider 原始结构化字段持久化池长、长度单位和分段事实。
- 历史数据只能从已保存的原始 FIT / provider facts 修复；确实缺事实的活动保持 `sample_missing` 或受控空态。

### 2. 公开水域标准距离指标仍处在半迁移状态

公开水域 catalog 已定义 `open_water_swim_750m`、`open_water_swim_1500m`、`open_water_swim_1900m`、`open_water_swim_3800m`、`open_water_swim_5k`、`open_water_swim_10k`，但这些 key 没有进入 `RECORD_METRIC_SERIES_SUPPORTED_KEYS`，因此 metric series API 会返回 `unsupported`。

与此同时，公开水域整次活动类指标已经有 materialized rows，例如 `open_water_longest_distance`、`open_water_longest_elapsed_time`，并可从 `get_career_records({sport: "open_water_swimming"})` 得到当前最佳。这说明问题不是“公开水域没有活动数据”，而是标准距离指标没有接入统一 V3 metric series / event materializer。

### 3. 旧测试和策略仍把游泳记录压在 candidate-only

当前公开水域 catalog 仍标记为 `candidate_only`，旧测试还断言泳池和公开水域 candidate 不应创建 active records。这与现在记录中心需要展示正式 current best / record progression 的产品目标冲突。

治理原则：

- 废弃“游泳只进 candidate、不进记录中心”的旧断言。
- 用质量门禁区分 `available`、`validation_required`、`sample_missing`，而不是让 candidate-only 变成无法进入记录中心的终点。
- 低置信或证据不足的记录可以进入待验证状态，但不能悄悄消失。

### 4. V2 列表路径对泳池和公开水域存在绕行

旧列表路径显式把 `open_water_swimming`、`pool_swimming` 放进跳过 derived fallback 的集合。这个策略在 V3 事实层没有完整接管前，会造成“活动存在，但记录中心列表为空”的表象。

治理原则：

- 记录中心列表只消费 metric result / current-best 派生结果。
- 当某个运动已经有 materialized result，空 key 应返回受控状态，而不是回退扫描或无声丢失。
- 不恢复 PB active/superseded 状态链作为主事实。

### 5. 前端存在记录中心缓存新鲜度问题

`track.html` 的记录中心按 `recordsBySport` 和 `careerSourceVersion` 复用缓存。后台 `refresh_career_derived_events()` 可以刷新派生事件，但当前链路没有保证刷新后递增或同步 `careerSourceVersion`。因此即使后端已修复，前端也可能继续显示旧的空快照。

治理原则：

- 前端不计算记录事实。
- 后端刷新、重建、删除活动、重新 materialize 后必须让前端 cache version 可感知。
- 保留同版本缓存复用，避免切 tab 全量重载。

## SWIM-REC-00：契约冻结与真实数据审计

目标：

- 冻结泳池和公开水域 record keys、scope、质量门禁、状态枚举和生命周期。
- 复核默认库中 `swimming`、`lap_swimming`、`open_water` 活动数量、字段完整性、points/tracks/laps/lengths 可用性。
- 明确哪些指标可以进入 `available`，哪些必须停在 `validation_required` 或 `sample_missing`。

必须输出：

- 游泳指标契约表。
- 默认库审计结果。
- 历史活动可修复 / 不可修复列表。
- 禁止从派生值反推事实的说明。

验收：

- 泳池缺池长活动不会被推断出池长。
- 公开水域有 GPS/距离/时间事实的活动可进入标准距离 resolver。
- 所有记录身份使用通用 `(activity_id, record_key, scope_hash)`，不出现 5K/10K 特例。

## SWIM-REC-01：泳池游泳源事实持久化

目标：

- 从 FIT / provider parser 到 Activity 存储链路追踪池长、单位、length/lap 事实。
- 在 source facts 中持久化 `pool_length_m`、pool unit、length index、stroke、duration、distance 等可证明字段。
- 确保导入、同步、更新、重建路径不会丢失这些事实。

允许修改：

- FIT / provider 解析层。
- Activity 写入和 schema migration。
- pool swim facts builder / resolver 输入结构。
- 对应 fixtures 和 tests。

禁止：

- 从总距离除以 lap 数猜池长。
- 在前端或展示层补字段。
- 只为某个品牌文件名写例外。

验收：

- 有 25m / 50m 池长事实的样例能生成对应泳池标准距离 metric results。
- 缺池长事实的真实活动保持 `sample_missing` 或 `validation_required`，且原因码稳定。
- 重新导入同一文件幂等，不产生重复结果。

## SWIM-REC-02：公开水域标准距离 metric series 接入

目标：

- 将公开水域标准距离 keys 加入统一 V3 supported set。
- 实现或接入公开水域标准距离 resolver。
- 基于真实 GPS/距离/时间事实生成 `open_water_swim_750m`、`1500m`、`1900m`、`3800m`、`5k`、`10k` metric results。

质量策略：

- 公开水域标准距离可以使用 activity-total tolerance 或距离流窗口，但必须写清规则。
- GPS 跳点、距离倒退、距离不足、时间缺失必须给出 reason code。
- 可进入 current best 的结果必须具备明确 eligibility。

验收：

- 任意满足距离/时间/质量规则的公开水域 10K 活动，应出现在 metric series、记录中心 current best 和时间轴里程碑。
- 不满足规则时，API 必须返回可解释状态，而不是 `unsupported` 或静默空列表。
- 最长距离、最长历时等整次活动类公开水域记录不受标准距离改造影响。

## SWIM-REC-03：游泳记录 current best / progression / timeline 联动

目标：

- 让泳池和公开水域的 metric results 统一派生 current best、record progression、record-breaking event 和 current-best event。
- 复用现有 `career_record_events` materializer，不新增平行事件系统。
- 活动删除、重新导入、修正字段后，记录中心和时间轴必须同时变化。

必须覆盖：

- `record_breaking`：按时间扫描成绩序列产生历史刷新节点。
- `current_best`：当前仍有效的最佳结果。
- 删除当前最佳活动后，旧 event 被移除或降级，下一条有效成绩晋升。
- 同一 `(activity_id, record_key, scope_hash)` 的 current-best 和 record-breaking 在时间轴展示时不产生互相矛盾的文案。

验收：

- 当前最佳不能仍以“刷新纪录”文案误导用户。
- 历史刷新记录保留为突破节点。
- 当前最佳进入时间轴 milestone。
- 删除任意泳池/公开水域当前最佳活动后，记录中心和时间轴同步更新。

## SWIM-REC-04：记录中心列表和前端缓存新鲜度修复

目标：

- 记录中心列表消费统一后端 current-best ViewModel。
- 后台刷新派生事件后，前端能感知 `careerSourceVersion` 或等价版本变化。
- 修复 `recordsBySport` 缓存保留旧空结果的问题。

要求：

- 前端仍然只消费后端事实。
- 不在 `track.html` 计算游泳记录、窗口、最佳、质量判断。
- 不禁用正常同版本缓存复用。

验收：

- 后端 materialize 后切换到公开水域 / 泳池 tab 能看到最新记录状态。
- 后台刷新完成后，不需要重启应用才能看到已生成的游泳记录。
- 缓存命中只发生在版本一致且数据未失效时。

## SWIM-REC-05：历史数据修复与受控空态

目标：

- 为历史游泳活动提供 rebuild / repair 路径。
- 只从现有原始文件、source ledger 或 provider payload 中提取事实。
- 生成或清理 `career_record_metric_results` 和 `career_record_events`。

验收：

- 公开水域历史活动重建后有标准距离和整次活动类结果。
- 泳池历史活动只有在原始事实足够时生成结果。
- 不可修复活动在记录中心展示受控状态和 reason code。
