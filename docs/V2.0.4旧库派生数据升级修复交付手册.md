# V2.0.4 旧库派生数据升级修复交付手册

## 1. 交付目标

老版本用户升级到 V2.0.4 之后，应用必须能在不重新导入 FIT、不要求用户手工清库的前提下，让旧库中已有的运动事实重新进入新版雷达图、记录中心和运动生涯消费链路。

本交付只修复派生层升级契约，不改变运动算法口径。

## 2. 核心事实链路

必须保留以下事实边界：

```text
activities raw/intermediate facts
-> backend resolver/materializer
-> derived fields / materialized tables / source version
-> pywebview API ViewModel
-> frontend rendering
```

前端只能消费后端 ViewModel 和状态字段，不能从 DOM、图表曲线、标题、距离或缺失字段反推运动事实。

## 3. 本轮强制修复范围

- `activities.advanced_metrics`：按当前 `CURRENT_METRICS_VERSION` 重建，使旧活动重新进入雷达图聚合。
- `career_record_metric_results`：全量重建支持的 record metric results。
- `career_record_events`：重新物化 current best 与 record breaking 事件。
- `career_race_events`、`career_pb_records`、`career_achievement_events`：刷新 Activity-backed 生涯事件，避免时间线和赛事/PB/成就继续读取旧派生状态。
- metric series cache / source version：重建完成后必须失效或刷新。
- `materialized_empty`：只有在派生完整且该 key 确实无可计算样本时才能返回。

## 4. 本轮审计与降级范围

- 力量训练热力图：只审计并保留/触发现有后端物化链路；原始 FIT 不可用时返回受控状态，不做前端猜测。
- 足迹 `region_admin1`：审计旧库缺失数量；若采用回填，必须复用离线 admin1 backfill，不改变 city-level 展示逻辑。
- 列表辅助指标：审计 `list_metric_backfill_version` 等旧状态，保留后台批处理策略，不能阻塞核心迁移。
- 旧库列差异：所有迁移/审计 SQL 必须兼容旧库列存在性差异。

## 5. 非目标

- 不修改 VAM 公式、雷达爬升评分、记录中心指标定义或 PB 计算口径。
- 不重新解析全部 FIT 作为默认升级修复手段。
- 不删除或覆盖 `activities`、`activity_source_files`、用户媒体或原始 FIT。
- 不引入某个用户库、某个活动 id、某个文件名的特例。
- 不让应用启动被大库全量重建长时间阻塞。

## 6. 升级机制

升级必须使用独立于 `_schema_meta.schema_version` 的迁移 key。建议 key：

```text
upgrade_2_0_4_derived_metrics_v1
```

状态至少包含：

```text
idle | running | completed | failed_retryable
```

成功后写入 `app_migrations` done 状态；失败不得写 done，下次启动可重试。

## 7. 数据安全与隐私

- 诊断输出只允许统计数量、状态、版本、错误 code。
- 不输出用户本机 FIT 绝对路径、token、账号信息或媒体路径。
- 写入前必须确保 schema ready。
- 重建过程必须幂等，重复执行不会产生重复事件或破坏用户确认状态。

## 8. 验收方式

每个任务必须至少运行针对性测试或等价本地验证。最终验收至少覆盖：

- 旧库 schema 已最新但派生迁移 key 未完成时，启动升级任务。
- 半物化 cycling 库不再用短骑行遮蔽 52km 历史活动。
- `cycling_fastest_10k / cycling_fastest_20k` 不再被部分物化误判为真实空。
- `advanced_metrics.metrics_version` 能升级到当前版本。
- 生涯事件刷新后，时间线与记录中心共享一致事实。
- 前端只展示后端升级状态并触发刷新，不计算事实。
- `git diff --check` 通过。
