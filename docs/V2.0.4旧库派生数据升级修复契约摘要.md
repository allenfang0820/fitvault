# V2.0.4 旧库派生数据升级修复契约摘要

## 1. 问题定义

旧库中的 Activity 原始 / 中间事实仍然存在，但新版雷达图、记录中心和运动生涯读取的派生字段、物化表或缓存没有统一升级，导致旧运动记录没有被新版功能正确消费。

本问题不是 VAM 算法错误，也不是必须重新导入 FIT 的问题。

## 2. 不可改变的契约

1. `activities` 是旧运动记录事实源。
2. 后端 resolver / materializer 负责从事实源重建派生数据。
3. 前端不得补算或猜测运动事实。
4. 派生升级不得依赖粗粒度 `_schema_meta.schema_version`。
5. 派生升级必须幂等、可重试、非破坏性。
6. 成功写 done；失败保持 retryable。
7. 不修改 VAM、雷达评分、记录指标或 PB 计算口径。

## 3. 强制重建契约

一次性派生升级完成后，必须满足：

- 旧活动的 `advanced_metrics` 符合当前 `CURRENT_METRICS_VERSION`。
- 支持的记录指标写入当前 resolver version 的 `career_record_metric_results`。
- `career_record_events` 包含基于当前 metric results 的 current best 与 record breaking 事件。
- PB / 赛事 / 成就派生事件经过当前 resolver 刷新。
- metric series cache 被清理或自然失效，前端能重新加载。

## 4. `materialized_empty` 契约

`materialized_empty` 不能只用“某个 sport 有任意物化行”判断。

允许返回 `materialized_empty` 的前提：

- 派生升级已完成；并且
- 该 `(sport, record_key, resolver_version)` 没有可计算样本；并且
- 后端能够给出稳定空态，而不是旧库半物化造成的缺失。

派生升级未完成时，API 应返回 `derived_rebuild_pending / derived_rebuilding`，或使用后端 resolver fallback。

## 5. 旧库兼容契约

迁移和审计代码不得假设所有新版列都存在。特别是 `activities.sport` 这类别名列可能不存在。

实现必须优先通过 schema introspection 或现有 ensure schema 入口确认表和列。

## 6. 审计型派生契约

- 力量热力图：只消费后端结构化力量事实；缺失时返回受控不可用状态。
- 足迹 admin1：省/州点亮消费 `region_admin1 / region_admin1_code` 或兼容后端 fallback；不得改写 city-level 展示语义。
- 列表辅助指标：后台补齐，不阻塞核心派生升级。

## 7. 前端契约

前端只允许：

- 查询派生升级状态。
- 展示“正在更新运动能力与记录数据”之类的状态。
- 在后端状态完成后刷新雷达图、记录中心和运动生涯缓存。

前端不允许：

- 计算 record metric。
- 判断哪条活动是最长/最快。
- 计算 VAM、雷达得分、力量肌肉、地区省份。
