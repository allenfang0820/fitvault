## 当前结论

默认库 `/Users/fanglei/.fitvault/user_profile.db` 当前没有 `trail_running` / `trail_run` 活动，也没有越野跑 metric results 或 timeline events。因此不能做真实库“越野跑记录已修复”的数据验收。

但代码层存在半迁移风险：

- 越野跑 catalog 中 5 个指标仍标记为 `candidate_only`。
- V3 `ACTIVITY_TOTAL_METRIC_SERIES_KEYS` 已包含 5 个越野跑整次活动指标：最长距离、最大累计爬升、最长历时、最高海拔、最大连续爬升。
- `trail_max_single_climb` 已接入 V3 metric series，可由轨迹海拔流生成 `career_record_metric_results`、current best、record progression 和 timeline events。
- 旧列表策略仍把 `trail_running` 放在跳过 derived fallback 的集合中；如果 V3 materialized result 不完整，会继续出现“列表空或指标缺失”的风险。

统一主线保持不变：

```text
Activity -> Record Metric Result -> Current Best / Record Progression -> Timeline Event / Records Center ViewModel
```

## 当前根因

### 1. 越野跑指标语义仍被旧 candidate-only 策略覆盖

`TRAIL_RECORD_DEFINITIONS` 中所有越野跑指标仍是 `candidate_only`。这与记录中心应展示 current best / progression 的产品目标不一致。旧 candidate 机制可以保留兼容，但不得作为越野跑记录中心的最终事实层。

治理原则：

- 记录中心事实层以 `career_record_metric_results` 为准。
- candidate-only 只作为低置信或待确认兼容路径，不得让具备 Activity 聚合事实的越野跑指标静默消失。
- 前端只能消费后端 ViewModel，不补算越野跑记录。

### 2. `trail_max_single_climb` 已进入 V3 metric series

越野跑最大连续爬升需要从轨迹海拔流解析区间，当前旧 evidence builder 能生成 candidate，但 V3 activity-total metric series 没有该 key。这会导致将来有真实越野跑数据时，其他 4 个指标可能进入记录中心，而最大连续爬升缺失。

治理原则：

- `trail_max_single_climb` 必须进入 `RECORD_METRIC_SERIES_SUPPORTED_KEYS`。
- 计算区间必须来自后端轨迹/海拔事实，保留 `range_json` 的 start/end 信息。
- 缺少轨迹或海拔流时返回受控空态和 reason code，不从总爬升反推单段爬升。

### 3. 默认库无真实样本，必须区分合成验证和真实验收

当前默认库无越野跑活动，因此只能验证：

- 空库/无样本时返回 `sample_missing`，不伪造 current best。
- 合成 fixture 的 V3 链路正确。
- 未来真实 Activity 进入后，rebuild/materialize 会自动写入 metric results 和 events。

不得把合成 fixture 验证表述为默认库真实数据验收。

## TRAIL-REC-01：越野跑 record key 与状态契约治理

目标：

- 明确 5 个越野跑指标的正式 V3 语义：
  - `trail_longest_distance`
  - `trail_max_ascent`
  - `trail_longest_elapsed_time`
  - `trail_max_altitude`
  - `trail_max_single_climb`
- 将具备后端事实的指标从旧 `candidate_only` 终点治理为可进入 `available` / `sample_missing` / `validation_required` 的 V3 状态。
- 保留旧 candidate 写入路径兼容，但不得作为 Records Center 主事实。

允许修改：

- `career_backend.py` 中越野跑 record definitions、catalog 状态、metric series supported keys。
- 越野跑相关测试。
- `docs/js_api_contract.json` 中必要的记录中心契约说明。

禁止：

- 增加路线 PR、路段 PR、GAP 曲线或路线对比。
- 将普通跑步、徒步、登山误归为越野跑。
- 前端补算越野跑指标。

验收：

- catalog 不再把具备 V3 链路的越野跑指标表达为不可进入记录中心的终点。
- 普通跑步、徒步、登山仍不会被越野跑 resolver 接收。
- API payload 不泄漏 raw track、文件路径、本地路径或设备序列号。

## TRAIL-REC-02：`trail_max_single_climb` 接入 V3 metric series

目标：

- 将 `trail_max_single_climb` 加入统一 V3 metric series supported set。
- 基于后端轨迹/海拔事实计算最大连续爬升，并写入 `career_record_metric_results`。
- `range_json` 必须包含可解释区间，例如 start/end 时间、距离或样本索引。

质量策略：

- 有有效海拔流和区间时进入 `available`。
- 缺轨迹、缺海拔、区间不可计算时返回 `sample_missing` 和稳定 reason code。
- 海拔流跳变或质量不足时进入 `validation_required` 或保留 reason code，不伪装成高置信。

验收：

- 合成越野跑 fixture 能生成 `trail_max_single_climb` metric result。
- 缺海拔/缺轨迹 fixture 不生成 current best，并返回受控 reason code。
- 不从总爬升 `gain_m` 反推最大连续爬升。

## TRAIL-REC-03：越野跑 current best / progression / timeline 联动

目标：

- 让 5 个越野跑指标统一派生 current best、record progression、`record_breaking` 和 `current_best` events。
- 复用现有 `career_record_events` materializer，不新增越野跑专用事件表。
- 活动删除或失效后，记录中心与时间轴同时更新，并晋升下一条有效成绩。

必须覆盖：

- 最高/最长类 higher-is-better 指标的 progression。
- 当前最佳进入时间轴 milestone。
- 同一 `(activity_id, record_key, scope_hash)` 的 current-best 不再同时以“刷新纪录”文案误导用户。
- 删除当前最佳后，旧 event 被清理，下一条有效成绩晋升。

验收：

- 合成 2-3 条越野跑活动能产生历史刷新和当前最佳。
- 当前最佳在时间轴展示为“最佳记录”，历史突破保留为“刷新纪录”。
- 删除当前最佳活动后，记录中心和时间轴同步变化。

## TRAIL-REC-04：记录中心列表、缓存版本与受控空态

目标：

- `get_career_records({sport: "trail_running"})` 消费统一后端 current-best ViewModel。
- 无真实越野跑活动时，记录中心、metric series 和 timeline 为空但状态可解释。
- 后台 materialize 后，前端记录中心缓存能随 `source_version` / `careerSourceVersion` 变化刷新。

要求：

- 前端不计算越野跑指标、最佳、质量或事件。
- 不禁用正常同版本缓存复用。
- 不恢复 PB active/superseded 作为记录中心主事实。

验收：

- 合成越野跑 materialized 后，Records Center 可读到 5 个指标的 current best。
- 默认库无越野跑时，不出现伪造 current best。
- 缓存命中只发生在版本一致且数据未失效时。
