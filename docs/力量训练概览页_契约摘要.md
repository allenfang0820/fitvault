## 2. 冻结产品范围

- 本期只展示基础训练指标、动作与训练组、前后人体肌肉热力图及基础联动。
- 不做力量训练复盘、趋势、PR、1RM、平衡判断、疲劳、恢复、疼痛、建议或 AI 解读。
- 页面回答“练了哪些动作/组/次数/重量”和“已记录动作的相对训练容量分布到哪些肌群”。
- 热力图表示基于已记录动作的相对训练分布，不代表肌电激活、疲劳或恢复状态。

## 3. 事实链路与责任边界

```text
FIT raw messages
  -> strength parser/normalizer
  -> activities 物化 JSON
  -> get_activity_detail() view model
  -> track.html 只读渲染
```

- 原始力量消息只在 FIT 导入、同步或版本化后台回填阶段解析；打开详情页不得重新读取 FIT。
- 动作和组来自 FIT 结构化消息；肌群来自版本化静态动作映射。
- 前端不得计算组容量、总容量、肌群权重、覆盖率、占比或视觉等级。
- 结构化数据缺失时保持 `strength_limited / strength_unavailable`，不得返回虚假空数组事实。
- 未识别动作保留在动作表中，但不得进入热力图；必须降低覆盖率并计入未映射数量。

## 3.1 v0.2 历史物化合同

冻结字段：

```text
strength_materialization_version INTEGER DEFAULT 0
strength_materialization_status  TEXT NULL
strength_materialization_error   TEXT NULL
```

冻结状态为 `pending / materialized / unstructured / source_missing / failed`。旧力量行缺少或低于
当前物化版本时是 `pending`，不能表述为设备无结构化数据；只有真实解析后无有效动作组才是
`unstructured`。详情返回 `detail.strength_materialization`，但仍只能读取 DB，不得现场解析 FIT。

回填候选必须是未软删除的明确力量活动，且解析路径经 resolve 后位于受控 TRACKS_DIR、为真实
`.fit` 文件。后台回填异步、单实例、限批、幂等，只更新力量 JSON、版本、状态、脱敏错误与
必要时间戳，不覆盖标题、赛事、地区、设备、天气等其他事实。

本地同步的未变化判断必须加入物化版本/状态：缺失或过期力量活动不能因 mtime/size 相同而
预跳过；普通活动继续快速跳过。生产 `user_profile.db` 写入前必须先 dry-run、展示候选、取得
用户明确确认，并使用 SQLite backup API 或 `.backup` 做一致性备份和 integrity_check。

## 4. 冻结状态合同

有真实结构化动作组：

```text
detail_surface_mode = strength
primary_visual = strength_muscle_map
split_section = strength_sets
overview_capabilities.has_structured_sets = true
```

无真实结构化工作组：

```text
detail_surface_mode = strength
primary_visual = strength_limited
split_section = strength_unavailable
overview_capabilities.has_structured_sets = false
```

- `has_structured_sets` 由物化的有效动作组事实决定，不能仅凭 `sport_type` 决定；工作组
  指标与热力图另外排除热身、放松和恢复组。
- 旧力量活动、无 `set_mesgs`、只有休息组或没有有效 repetitions 的活动安全降级。
- 复盘入口仍只对 `endurance_outdoor` 开放；本项目不得顺带开放力量复盘。

## 5. 数据合同

活动持久化新增可空 JSON 字段：

```text
strength_sets_json
strength_summary_json
muscle_heatmap_json
```

- 旧行迁移后为 `NULL`。
- 重导入同一 FIT 幂等覆盖，不追加重复组。
- `strength_sets_json` 保留组序、规范化动作、组类型、次数、重量、时长和来源。
- `set_type=active` 且 repetitions 大于 0 表示有效动作组；关联 workout step 的
  `intensity=warmup/cooldown/recovery` 时分别规范化为非工作组，只有其余有效动作组计入工作组。
- `total_volume_kg = sum(repetitions * weight_kg)`，缺失或非正重量不进入总容量。
- 无重量但有次数的映射动作可以按次数进入相对肌群分布。
- 所有缺失事实使用 `null`，不得用 `0` 冒充；FIT 明确记录 `weight=0` 时规范化为无外部重量。

## 6. FIT 消息探针结论

首次本地只读扫描发现 196 个候选力量文件，186 个含 `set_mesgs`，足以覆盖全重量、部分
重量、自重/无重量和无结构化组四类。真实文件不进入仓库，只保留脱敏受控快照。

候选消息：

```text
set_mesgs
exercise_title_mesgs
workout_step_mesgs
```

当前冻结的关联优先级：

1. `set_mesgs[].wkt_step_index` 关联 `workout_step_mesgs[].message_index`。
2. 动作标题使用 `exercise_category + exercise_name` 关联 `exercise_title_mesgs`；不能假设标题
   消息的 `message_index` 等于 workout step index。
3. 没有 workout step 时，保留 set 的首个有效 `category`；`category_subtype` 仅在 Garmin
   profile 能可靠解析时用于具体动作名。
4. 旧文件可能把 subtype 暴露为数字键 `2`，也可能给出多个 category/subtype 值；在
   ST-01 未证明稳定前不得猜具体动作。
5. `set_type=rest` 不计工作组；`active` 但 repetitions 缺失或为 0 不计第一期工作组。

ST-02 刷新：ST-01 证明 `set_type=active` 中可包含 `intensity=warmup/cooldown`。因此结构化
存在性与工作组统计分开：前者由有效动作组决定，后者排除已明确标记的热身、放松和恢复组。

## 7. UI 合同

- `strength_muscle_map` 使用独立宽布局，不继承 `.overview-track-area` 的 260px 约束。
- `strength_muscle_map` 必须真正隐藏标准概览容器；CSS 不得覆盖 `hidden` 属性导致轨迹缩略图、
  圈速统计或赛事照片面板残留。
- 所有非户外详情页只展示后端声明的基础事实和可用专项分段；没有 `track_map` 时隐藏轨迹主视觉，
  没有 `laps/indoor_segments/swim_lengths` 表格合同时隐藏分段区。
- 大于等于 1024px 时前后人体并排；小于 760px 时使用正面/背面分段切换。
- 只消费 `detail.strength` 和后端 `overview_metrics`；不显示路线、圈速、天气、海拔、
  环境挑战或复盘入口。
- 动作表语义化展示动作、工作组、每组次数/重量、容量和主要肌群；已知动作在后端 view model
  中展示中文名，保留 `exercise_key` 和可选 raw name 作为追溯事实。
- 颜色之外必须提供文字等级、可聚焦说明和选中状态。
