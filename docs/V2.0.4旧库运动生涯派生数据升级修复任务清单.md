# V2.0.4 旧库派生数据升级修复任务清单

## 0. 背景与目标

Windows 老版本用户升级到 V2.0.4 后，历史导入的 FIT 活动原始 / 中间事实仍在，例如 `track_json`、`points_json`、`dist_km`、`gain_m` 等字段足够当前雷达图和记录中心计算所需数据，但派生表可能处于旧版本或半物化状态。

典型表现：

- `career_record_metric_results` 只包含少量近期短骑行。
- `最长骑行距离` 读到短骑行，而不是历史 52km 活动。
- `最快 10K / 20K` 等记录没有物化行，页面显示无数据。
- 因为 cycling 已存在部分物化结果，API 返回 `materialized_empty`，不再现场 fallback。
- `advanced_metrics` 虽然字段存在，但不是当前 `CURRENT_METRICS_VERSION` 或未按当前雷达图消费契约完整重建，导致旧活动不能进入新版雷达聚合。

本次修复目标：让 V2.0.4 之后的应用在首次打开旧库时，自动完成雷达图与运动生涯派生层升级修复，用户只需安装或升级安装包，无需重新导入 FIT。

同类潜在问题也必须纳入审计：凡是“旧活动事实仍在，但新版功能读取的是升级后新增 / 改版的派生字段、物化表或缓存”的链路，都需要明确分类为本轮强制迁移、后台按需修复、或暂不纳入。

## 1. 明确非目标

- VAM 算法不是本轮问题范围；不修改 VAM 计算公式、雷达爬升评分、雷达解释文案。
- 旧活动 `advanced_metrics` 未按当前雷达图版本重建属于本轮范围；需要修复旧数据不被新版雷达消费的问题。
- 不要求用户删除数据库、重新导入 FIT、重新解析全部 FIT 文件。
- 不在 `track.html` 或前端缓存里补算记录事实。
- 不用某个具体活动、某个文件名、某个 Windows 用户库写特例。
- 不让前端根据 DOM、曲线或缺失字段猜测运动类型、肌肉、地区、记录或训练事实。
- 不改变已确认的记录中心主链路：

```text
Activity -> career_record_metric_results -> current_best / record_breaking -> career_record_events -> Records Center ViewModel
```

## 2. 修复原则

- 派生数据必须可以从现有 `activities` 表事实重建，包括 `advanced_metrics` 与记录中心 metric results。
- 升级修复必须幂等：重复启动、重复执行不会产生重复记录或破坏已有用户数据。
- 迁移哨兵必须独立于粗粒度 `_schema_meta.schema_version`。
- 迁移成功后才写入 done 状态；失败时保留可重试能力。
- API 读路径不能因为某个 sport 有少量物化行，就把缺失 record key 永久解释为真实空数据。
- 前端只消费后端状态：可展示“正在更新运动能力与记录数据”，但不自行推导记录。
- 升级 SQL / 诊断 SQL 必须兼容旧库列差异：不能假设 `activities` 一定存在 `sport` 等新版别名列；应按 `PRAGMA table_info` 或等价 schema introspection 构造查询。
- 对同类派生链路进行分级处理：
  - 强制迁移：影响新版雷达、记录中心、运动生涯核心事实的派生层。
  - 后台按需修复：依赖原始 FIT 文件仍可访问的增强展示，例如力量训练肌肉热力图。
  - 独立低优先级修复：不阻断核心记录但影响展示完整性的派生事实，例如足迹 admin1。

## 3. 允许修改范围

- `main.py`
  - 启动升级入口。
  - 派生数据升级协调函数。
  - 必要的后台状态 / API 暴露。
- `career_backend.py`
  - `career_record_metric_results` 全量重建入口。
  - `career_record_events` current best / record breaking 重新物化。
  - metric series cache 清理或失效。
  - `materialized_empty` 的保护逻辑。
- `profile_backend.py`
  - 复用现有 `app_migrations` 读写能力；如必须扩展，只做幂等轻量扩展。
- `track.html`
  - 只允许增加后端状态展示和刷新触发，不允许前端计算记录事实。
- `tests/`
  - 增加旧库半物化、迁移幂等、API fallback / 待重建状态相关测试。
- `docs/js_api_contract.json`
  - 如新增或调整 API 返回字段，必须同步契约。

## 5. DERIVED-UPGRADE-00：冻结旧库半物化复现夹具

### 目标

- 构造一个最小 SQLite 测试库：
  - `activities` 中有一条历史 52km cycling 活动。
  - 同库中另有两条近期短骑行。
  - `career_record_metric_results` 只物化近期短骑行。
- 复现记录中心错误：
  - `cycling_longest_distance` 当前最佳错误指向短骑行。
  - `cycling_fastest_10k` / `cycling_fastest_20k` 因缺物化行返回 `materialized_empty` 或等价空态。

### 验收

- 测试能在当前代码下失败，并准确描述“半物化阻断 fallback”。
- 夹具不包含真实用户路径、真实 FIT 文件路径或隐私字段。

## 5B. DERIVED-UPGRADE-00B：派生数据依赖审计与旧库列兼容基线

### 目标

- 梳理新版页面 / API 读取的所有派生字段、物化表和内存缓存，至少覆盖：
  - 雷达图：`activities.advanced_metrics`。
  - 记录中心：`career_record_metric_results`、`career_record_events`、metric series cache。
  - 运动生涯时间线：`career_race_events`、`career_pb_records`、`career_achievement_events`。
  - 力量训练详情：`strength_sets_json`、`strength_summary_json`、`muscle_heatmap_json`、`strength_materialization_version`、`strength_materialization_status`。
  - 足迹地图：`region_admin1`、`region_admin1_code`。
  - 列表 / 生涯辅助指标：`avg_power`、`max_power`、`normalized_power`、`avg_stroke_distance`、`swolf`、`list_metric_backfill_version`。
- 将每条链路分类为：
  - 本轮必须强制迁移。
  - 本轮只做状态审计和安全提示。
  - 本轮明确不处理，并说明不影响旧运动记录被核心功能消费的原因。
- 建立旧库列兼容基线：
  - 不假设 `activities.sport` 一定存在。
  - 不假设所有新版派生列一定存在。
  - 查询前必须通过 schema introspection 或现有 ensure schema 入口确认列存在。

### 验收

- 输出一份审计结果，能说明每个新版功能读取哪个后端事实源。
- 半旧 Windows 库即使缺少某些别名列，也不会在迁移 SQL 中直接报 `no such column`。
- 审计结论明确：VAM 算法不变，但雷达所需旧活动 `advanced_metrics` 必须重建。
- 审计结论明确：力量热力图不能由前端猜测；只能由 FIT 结构化力量事实物化或显示受控不可用状态。

## 6. DERIVED-UPGRADE-01：设计派生升级哨兵与状态契约

### 目标

- 新增独立迁移 key，例如：

```text
upgrade_2_0_4_career_record_derived_v1
```

- 使用现有 `app_migrations` 表记录 done 状态。
- 设计升级状态字段，至少覆盖：
  - `idle`
  - `running`
  - `completed`
  - `failed_retryable`
- 明确迁移成功后写 done，失败不写 done。

### 验收

- 不依赖 `_schema_meta.schema_version` 是否已是最新。
- 重复执行不会重复写入记录事件。
- 迁移失败后下一次启动可重试。

## 7. DERIVED-UPGRADE-02：实现一次性派生层升级协调器

### 目标

- 在应用启动后检查迁移 key。
- 如果未完成，启动一次后台派生升级任务。
- 升级过程不得阻塞主窗口打开；旧库大时允许后台运行。
- 运行期间暴露只读状态给前端。

### 建议流程

```text
ensure schema
-> check app_migrations key
-> set in-memory state running
-> rebuild activities.advanced_metrics
-> rebuild career_record_metric_results
-> rematerialize record events
-> clear caches
-> mark app_migration_done
-> set state completed
```

### 验收

- 新用户空库不会报错。
- 旧库首次启动会执行一次。
- 已完成迁移的库再次启动不执行重建。
- 迁移中断或异常时不会写 done。

## 8. DERIVED-UPGRADE-03：重建雷达图 advanced_metrics

### 目标

- 重建旧活动的 `activities.advanced_metrics`，使其符合当前 `CURRENT_METRICS_VERSION` 和新版雷达图消费契约。
- 复用现有高级指标计算入口，例如 `force_rebuild_all_records(force=True)` 或等价受控函数。
- 不修改 VAM 公式、雷达爬升评分公式或雷达维度定义。
- 不重新解析 FIT 文件；只使用数据库中已有 `track_json` / `points_json`。

### 验收

- 旧库中有有效轨迹事实的历史活动，升级后 `advanced_metrics.metrics_version` 为当前版本。
- 雷达图聚合能消费重建后的旧活动。
- 没有轨迹点或事实不足的活动被安全跳过，并返回可统计的 skipped / reason。
- VAM 算法、阈值和雷达评分逻辑无业务变更。

## 9. DERIVED-UPGRADE-04：全量重建记录中心 metric results

### 目标

- 调用或增强 `career_backend.rebuild_career_record_metric_results(..., dry_run=False)`。
- 覆盖所有 supported record keys 和所有 supported sports。
- 确保历史 cycling 活动可生成：
  - `cycling_longest_distance`
  - `cycling_longest_elapsed_time`
  - `cycling_max_ascent`
  - `cycling_fastest_10k`
  - `cycling_fastest_20k`
  - 其他当前已接入的 cycling metric series key

### 验收

- 52km cycling 活动无需重新导入即可进入 `career_record_metric_results`。
- 重建后 `cycling_longest_distance` current best 指向真实最长活动。
- 具备距离 / 时间事实的 10K / 20K 成绩不再返回 `materialized_empty`。
- 无法计算的记录保留稳定 reason code，而不是静默空。

## 10. DERIVED-UPGRADE-05：重新物化 current best / record breaking events

### 目标

- 基于重建后的 `career_record_metric_results` 重新生成：
  - `record_breaking`
  - `current_best`
- 清理同一 record key 下已经过时的 metric-series 事件。
- 保持事件身份稳定：

```text
activity_id + record_key + scope_hash + event_type
```

### 验收

- 记录中心 current best 与时间轴 current best 一致。
- 历史刷新纪录保留为 progression。
- 当前最佳不再被旧短骑行事件覆盖。
- 重复重建不会产生重复 `career_record_events`。

## 10B. DERIVED-UPGRADE-05B：刷新 PB / 赛事 / 成就派生事件

### 目标

- 在派生升级协调器中明确刷新运动生涯 Activity-backed 派生事件：
  - `career_race_events`
  - `career_pb_records`
  - `career_achievement_events`
- 复用 `career_backend.refresh_career_derived_events(include_pb=True)` 或等价后端入口。
- 确保生涯时间线、赛事节点、PB 节点、成就节点都基于当前 resolver 重新生成。
- 保持用户确认 / 拒绝过的记录状态不被无条件覆盖；需要先审查现有状态字段与 resolver 写入语义。

### 验收

- 旧库升级后，运动生涯时间线不再依赖旧版本残留的 PB / 赛事 / 成就派生表。
- 赛事相册入口如依赖赛事事件，能读取刷新后的 `career_race_events`。
- PB 与记录中心 current best 的事实来源不互相矛盾。
- 重复执行不会产生重复赛事、PB 或成就事件。

## 10C. DERIVED-UPGRADE-05C：审计力量热力图、足迹 admin1、列表指标 backfill

### 目标

- 力量训练热力图：
  - 审计旧力量活动的 `strength_materialization_status` 和 `strength_materialization_version`。
  - 若保存的原始 FIT 文件仍在受控目录内，可后台按需补齐 `strength_sets_json`、`strength_summary_json`、`muscle_heatmap_json`。
  - 若原始 FIT 文件不可用，返回受控状态，例如 `source_missing` / `strength_limited`，不得重新导入或前端猜测肌肉。
- 足迹 admin1：
  - 审计旧活动中 `region_status='success'` 但 `region_admin1 / region_admin1_code` 为空的数量。
  - 复用现有离线 admin1 backfill 能力时，不改变 city-level 展示、标题命名和现有地区回填主逻辑。
  - 如不纳入本轮强制迁移，必须记录为独立低优先级旧库展示修复项。
- 列表 / 生涯辅助指标 backfill：
  - 审计骑行功率、水上运动指标等 `list_metric_backfill_version` 仍旧的活动。
  - 保留现有后台批处理策略，避免启动时阻塞。
  - 对原始文件路径不可用的活动给出稳定 reason，不误报为真实无数据。

### 验收

- 旧库力量训练详情不会因为新版肌肉热力图字段缺失而出现前端假数据。
- 旧库足迹地图 admin1 缺失有统计、有决策：本轮修复或单独排期。
- 旧库列表辅助指标缺失不会阻断核心雷达 / 记录中心修复。
- 所有审计输出不得泄露本机绝对路径、FIT 文件原始路径、账号或 token。

## 11. DERIVED-UPGRADE-06：修复半物化下的 `materialized_empty` 保护

### 目标

- 防止“某个 sport 有任意物化行”被误认为“该 sport 所有 record key 都已完整物化”。
- 对缺失 record key 增加更严格的判断：
  - 如果派生升级未完成：返回 `derived_rebuild_pending` / `derived_rebuilding`，或允许 resolver fallback。
  - 如果派生升级已完成且该 key 确实没有可计算样本：才允许 `materialized_empty`。

### 可选策略

优先方案：

- 用迁移 key / 物化完整性状态控制 `materialized_empty`。
- 旧库未完成派生升级时，metric series API 可以临时 fallback 扫描 `activities`。

备选方案：

- 为 `career_record_metric_results` 引入 materialization batch/version 统计。
- 按 `(sport, record_key, resolver_version)` 判断完整性，而不是按 sport 粗判断。

### 验收

- 半物化 cycling 库查询 `cycling_fastest_10k` / `cycling_fastest_20k` 不再直接返回错误空态。
- 已完成升级且真实无样本的 key 仍可返回受控空态。
- 不引入大库下每次打开记录中心都全量扫描的性能回退。

## 12. DERIVED-UPGRADE-07：前端展示后台升级状态并刷新雷达 / 记录缓存

### 目标

- 前端从后端读取派生升级状态。
- 迁移运行中展示类似：

```text
正在更新运动能力与记录数据，完成后将自动刷新。
```

- 迁移完成后清理或刷新雷达图和记录中心缓存。

### 要求

- 前端不计算任何 record metric。
- 前端不判断 52km 是否应该是最长骑行。
- 前端不计算 VAM 或雷达得分。
- 只根据后端返回的状态、metrics version、source version 或 refresh signal 触发重新加载。

### 验收

- 旧库首次打开时用户能看到升级提示。
- 升级完成后无需重启即可看到新版雷达和正确记录。
- 同一版本、未变化数据仍可复用缓存。

## 13. DERIVED-UPGRADE-08：回归测试与 Windows 打包前验收

### 必须新增或更新测试

- 旧库 schema 已最新，但 `app_migrations` 未写派生升级 key 时会触发重建。
- 旧库 `advanced_metrics` 缺失或版本旧时，启动派生升级会重建到当前 `CURRENT_METRICS_VERSION`。
- 半物化 cycling 库重建后：
  - `cycling_longest_distance` 指向 52km。
  - `cycling_fastest_10k` 有数据。
  - `cycling_fastest_20k` 有数据。
- 已完成迁移 key 的库不会重复重建。
- 重建失败不写 done，下一次可重试。
