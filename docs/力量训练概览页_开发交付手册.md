# 脉图力量训练概览页开发交付手册

> 版本：v0.2  
> 状态：已重开；ST-01 至 ST-06 已完成，历史活动物化修复待开发  
> 基线日期：2026-07-29  
> 适用范围：活动详情页「概览」Tab 中 `strength_training` 的结构化训练详情  
> 不包含范围：力量训练复盘、历史趋势、AI 建议、恢复判断

## 0. 交付目标

为 Garmin FIT 中包含结构化动作组数据的力量训练，提供一张以肌肉热力图为主视觉的活动概览页。

v0.2 追加升级目标：已存在于数据库中的历史力量活动，只要其受控本地 FIT 仍包含结构化
动作组，也必须通过版本化后台回填获得相同能力；不得要求用户删除、改名或手动重复导入 FIT。

页面只回答两件事：

```text
本次练了哪些动作、每组做了多少次和多重？
这些已记录动作的训练容量主要分布到哪些肌群？
```

页面不回答疲劳、恢复、进步、偏科、训练建议或伤病风险问题；这些属于未来复盘能力。

## 1. 当前基线与改造边界

### 1.1 当前实现

当前活动详情页由以下组件构成：

```text
track.html
  -> renderActivityDetail()
  -> record.detail 视图模型

main.py
  -> _build_multi_sport_overview_view_model()
  -> _build_activity_detail_summary_from_row()
  -> _build_record_from_row()

fit_engine.py
  -> FITCoreEngine.parse_fit_file()
  -> FITCoreEngine.parse_fit_file_raw()
```

ST-01 至 ST-06 完成后：

- `strength_training` 已归类为 `detail_surface_mode="strength"`。
- 新导入或实际重解析的结构化力量 FIT 已能物化动作组、摘要和肌肉热力图。
- `track.html` 已具备独立宽布局、前后人体图、动作表、移动端切换和降级渲染。
- 无结构化动作数据时仍使用 `primary_visual="strength_limited"`、
  `split_section="strength_unavailable"`。
- schema migration 只为历史行新增了可空 JSON 列，没有重新解析其本地 FIT；本地同步又按
  `file_path + file_mtime + file_size` 跳过未变化文件，因此历史结构化活动会被错误留在
  `strength_limited`。

### 1.2 本次必须改变的边界

结构化力量训练进入新的详情态：

```text
detail_surface_mode = "strength"
primary_visual     = "strength_muscle_map"
split_section      = "strength_sets"
has_structured_sets = true
```

无结构化动作组的旧态必须保留：

```text
primary_visual      = "strength_limited"
split_section       = "strength_unavailable"
has_structured_sets = false
```

严禁根据活动标题、心率、时长、热量或 AI 猜测动作、组数、重量、训练量或肌群。

### 1.3 交付后真实数据证据

2026-07-29 对截图对应活动执行只读核验：

```text
sample_id = local_strength_regression_1
historical activity row exists = true
strength_sets_json / strength_summary_json / muscle_heatmap_json = NULL
source FIT exists = true
```

同一 FIT 实际包含 56 条 `set_mesgs`：28 个有效动作组、28 个休息组，338 次，28 个动作组
均有重量，总训练容量 7420kg。当前 resolver 可生成 11 个肌群区域且映射覆盖率为 100%。

这证明截图不是前端渲染失败，也不是 FIT 无数据，而是历史活动缺少物化迁移。真实 FIT 文件、
用户路径和可识别元数据不得进入仓库；测试只能保留脱敏消息快照。

## 2. 产品范围

### 2.1 本期包含

- 基础训练指标：训练时长、动作数、有效组数、总次数、总训练容量、平均心率或热量。
- 动作及训练组：动作名、工作组、每组次数、每组重量、单动作训练容量。
- 前后人体肌肉热力图。
- 热力图与动作表之间的基础联动。
- 完整、部分、缺失结构化数据三种清晰降级状态。
- 历史结构化力量活动的后台物化、进度状态和失败降级。

### 2.2 本期不包含

- 近 4 周趋势、单动作历史对比、PR、估算 1RM。
- 推拉/上下肢/动作模式平衡判断。
- 肌肉疲劳、恢复、疼痛、受伤、训练建议、AI 解读。
- 用户手动编辑 FIT 动作、组数或重量。
- 第三方力量训练应用导入。
- 依据心率、时长或卡路里生成肌肉图。

## 3. 概览布局

力量训练不得继承户外活动的「260px 轨迹缩略图 + 圈速表 + 侧栏」布局。

### 3.1 桌面端

```text
活动标题 / 日期 / 设备

训练时长 | 动作数 | 有效组数 | 总次数 | 总训练容量 | 平均心率或热量

┌──────────────────────────────────────┬─────────────────────────────────────┐
│ 肌肉分布                              │ 动作与训练组                        │
│                                      │                                     │
│      前视人体        后视人体          │ 动作           工作组    次数 x 重量 │
│      热力分区        热力分区          │ 杠铃深蹲       4 组     8 x 80 kg   │
│                                      │ 杠铃卧推       4 组     10 x 60 kg  │
│  图例：低 / 中 / 高                   │ 坐姿划船       3 组     12 x 45 kg  │
│  点击肌群后高亮相关动作               │                                     │
└──────────────────────────────────────┴─────────────────────────────────────┘
```

推荐约束：

- 肌肉图为全宽主模块的一部分，不再放进现有 `.overview-track-area`。
- 桌面端采用两列：肌肉图区域 `minmax(520px, 1.25fr)`，动作表区域 `minmax(360px, 0.9fr)`。
- 人体前后视图并排显示，不要求用户切换；每个视图保持相同宽高比。
- 肌肉图区域最小高度为 `420px`，优先保证肩、躯干、手臂与腿部区块可读。
- 基础指标位于人体图上方，为 3 至 6 个等宽指标卡；缺失指标不以 `0` 补位。
- 不显示路线、圈速、天气、海拔、环境挑战、训练收益或复盘入口。

### 3.2 窄屏

```text
基础训练指标
前视人体 / 后视人体切换
肌肉图图例与选中肌群摘要
动作与训练组表
```

- 宽度小于 `760px` 时，人体图只展示一个视图，使用「正面 / 背面」分段控制切换。
- 动作表位于肌肉图下方，保留完整列语义；必要时允许表格容器横向滚动。
- 不能通过缩小文字或压扁人体图来硬塞双视图。

### 3.3 交互

- 悬停或键盘聚焦肌肉区块：显示肌群名、相关动作数、有效组数和本次分布占比。
- 点击肌肉区块：高亮右侧相关动作；再次点击取消选择。
- 点击动作行：高亮其主练与辅助肌群，主练与辅助使用不同透明度，不只依赖颜色表达。
- 默认不选中任何动作或肌肉，首屏即可读。

## 4. 数据展示规则

### 4.1 基础指标

| 指标 | 字段 | 展示条件 | 说明 |
| --- | --- | --- | --- |
| 训练时长 | `duration_sec` | 大于 0 | 必显 |
| 动作数 | `distinct_exercise_count` | 大于 0 | 按规范化动作聚合 |
| 有效组数 | `working_set_count` | 大于 0 | 仅工作组；热身、恢复和无效组不计入 |
| 总次数 | `total_reps` | 大于 0 | 仅可确认 repetitions 的工作组 |
| 总训练容量 | `total_volume_kg` | 大于 0 | `sum(reps * weight_kg)`；无重量的组不计入该值 |
| 平均心率 | `avg_hr` | 非空 | 可选 |
| 消耗热量 | `calories` | 大于 0 | 当平均心率缺失或指标卡空间允许时显示 |

本期不显示估算 1RM、RPE、休息时间、训练效果、肌肉恢复或任何与历史比较相关的字段。

### 4.2 动作与训练组

动作表按动作聚合，默认按训练发生顺序排列。

| 列 | 字段 | 规则 |
| --- | --- | --- |
| 动作 | `exercise_name` | 使用 FIT 标题或已知枚举映射；未知时显示原始类别或“未识别动作” |
| 工作组 | `working_set_count` | 不包含热身、恢复或无 repetitions 的组 |
| 训练组 | `set_display` | 相同组可合并为 `4 x 8 x 80 kg`；重量或次数不同则逐组展开 |
| 容量 | `volume_kg` | 有可靠重量时显示；否则显示 `--` |
| 主要肌群 | `primary_muscles` | 仅展示映射表中可确认的肌群 |

“未识别动作”可以出现在动作表中，但不得进入肌肉热力图；页面应显示未映射动作/组数量，避免用户误以为热力图已覆盖全部训练。

## 5. FIT 解析与持久化

### 5.1 解析时机

只允许在 FIT 导入、同步或版本化后台回填阶段解析原始力量训练消息：

```text
FIT 文件
  -> FITCoreEngine.parse_fit_file_raw()
  -> 解析结构化训练组
  -> 规范化动作和组
  -> 写入活动持久化字段
  -> get_activity_detail() 返回详情 view model
```

禁止在用户打开活动详情页时重新读取或解析 FIT 文件。详情读取路径必须只消费数据库中已物化的结构化结果。

### 5.2 候选消息

实现必须先用真实 Garmin Strength FIT 样本验证消息字段，再冻结最终字段名。优先检查：

```text
set_mesgs
exercise_title_mesgs
workout_step_mesgs
```

常见候选事实包括动作类别、动作标题、组类型、次数、重量、持续时间、开始时间和组序号。字段缺失时保持 `null`，不得虚构默认值。

### 5.3 推荐持久化结构

第一期沿用当前 `laps_json` 的局部 JSON 持久化风格，新增：

```text
activities.strength_sets_json
activities.strength_summary_json
activities.muscle_heatmap_json
```

建议的 `strength_sets_json`：

```json
[
  {
    "set_index": 1,
    "exercise_key": "barbell_squat",
    "exercise_name": "Barbell Squat",
    "set_type": "working",
    "reps": 8,
    "weight_kg": 80.0,
    "duration_sec": 32,
    "source": "fit_set_mesgs"
  }
]
```

建议的 `strength_summary_json`：

```json
{
  "distinct_exercise_count": 5,
  "working_set_count": 16,
  "total_reps": 128,
  "total_volume_kg": 8470.0,
  "unmapped_set_count": 1,
  "weight_missing_set_count": 2,
  "source": "fit_set_mesgs"
}
```

建议的 `muscle_heatmap_json`：

```json
{
  "source": "fit_set_mesgs + muscle_map_v1",
  "coverage": {
    "mapped_working_sets": 15,
    "unmapped_working_sets": 1,
    "mapped_volume_share_pct": 92.0
  },
  "regions": [
    {
      "id": "quadriceps",
      "label": "股四头肌",
      "side": "front",
      "score": 1.0,
      "level": "high",
      "share_pct": 31.4,
      "exercise_keys": ["barbell_squat"]
    }
  ]
}
```

JSON 字段必须在活动重导入时可幂等覆盖；删除活动时与现有活动数据一起清理。

### 5.4 历史活动物化迁移

新增显式物化状态，不得用三个 JSON 是否为空同时表达“未处理、无结构化数据、源文件缺失、
解析失败”四种不同事实。冻结字段：

```text
activities.strength_materialization_version INTEGER DEFAULT 0
activities.strength_materialization_status  TEXT
activities.strength_materialization_error   TEXT
```

冻结状态：

```text
pending        等待后台回填；不得宣称设备未提供结构化数据
materialized   三个 JSON 已按当前版本物化
unstructured   已解析源 FIT，但没有有效结构化动作组
source_missing 源路径缺失、越界或不是受控 FIT
failed         解析或写入失败；允许后续重试
```

历史活动 schema migration 后，未软删除的力量活动初始化为 `pending/version=0`；非力量活动
保持 status 为 `NULL`。新导入力量 FIT 在同一持久化事务内直接落为 `materialized` 或
`unstructured`，不能先写 ready 再依赖后台补齐。

回填候选必须同时满足：

- 活动未软删除，且 `sport_type/sub_sport_type` 明确为 `strength_training`。
- 物化版本低于当前 `STRENGTH_MATERIALIZATION_VERSION`，或三个 JSON 仍缺失。
- `file_path` 经 `resolve()` 后位于受控 `TRACKS_DIR`，扩展名为 `.fit`，文件真实存在。

后台 worker 必须：

- 启动后异步、单实例、限批处理，不阻塞主窗口；详情 API 绝不现场解析 FIT。
- 复用 `normalize_strength_messages()` 与 `resolve_strength_muscle_heatmap()`，不得复制算法。
- 每个活动在短事务中只更新力量 JSON、物化版本/状态/错误和必要的 `updated_at`；不得覆盖
  用户标题、赛事标记、地区、设备、天气或其他活动事实。
- 对无结构化数据、源缺失和失败分别落状态；错误文本必须脱敏、限长，不返回本地路径。
- 具备 dry-run、进度、成功/跳过/失败计数和幂等重跑；完成前不得把 migration 标记为成功。

本地同步的“文件未变化”判断必须同时检查力量物化版本。未物化或版本过期的力量活动即使
mtime 与 size 未变，也必须进入受控重解析；普通活动仍保持现有快速跳过行为。

## 6. 动作到肌群的映射

### 6.1 映射表

新增版本化静态映射，例如：

```text
strength_muscle_map_v1.py
```

每个动作定义：

```python
{
    "primary": {"quadriceps": 1.0, "glutes": 0.65},
    "secondary": {"hamstrings": 0.35}
}
```

第一期肌群区域建议限制为：

```text
胸部
背阔肌
上背
前三角
侧/后束三角肌
肱二头肌
肱三头肌
核心
臀部
股四头肌
腘绳肌
小腿
```

不做左右侧拆分，除非 FIT 记录明确给出单侧动作事实。

### 6.2 热度规则

热力图表示“本次训练的相对容量分布”，不是实际生理激活或疲劳。

```text
有重量的组分数 = repetitions * weight_kg
无重量但有次数的组分数 = repetitions
肌群分数 = sum(组分数 * 动作肌群权重)
肌群占比 = 肌群分数 / 全部已映射肌群分数
```

视觉层将肌群分数归一化为 `0.0 - 1.0`，再映射为 `low / medium / high`。原始训练容量、映射权重和可视化等级必须分开保存；前端不得自行计算。

### 6.3 数据边界

- 动作无法映射时：保留动作和训练组，排除出肌肉图，并计入 `unmapped_set_count`。
- 重量缺失时：动作和次数仍可参与相对分布，但不计入 `total_volume_kg`。
- 仅有活动时长、心率和热量时：使用 `strength_limited`，不显示空白人体图。
- 肌肉图须在图例或辅助文案中表达“基于已记录动作的训练分布”。

## 7. 人体图开源方案

### 7.1 首选

候选库：`vulovix/body-muscles`

采用条件：

- 可使用原生 HTML/JavaScript，不要求将当前 `track.html` 重构为 React。
- 具备前后人体视图、可指定肌肉强度、悬停/点击事件和 SVG 分区。
- 采用 Apache-2.0 许可。

集成方式：

```text
上游固定版本
  -> 下载或 vendor UMD 构建与所需 SVG
  -> 放入本地 lib/
  -> 由 track.html 本地加载
```

禁止运行时 CDN 依赖，确保桌面端离线可用且版本可审计。

### 7.2 风险与决策

- 该库功能适配当前项目，但社区体量有限；首次开发前必须完成本地 POC。
- POC 重点验证：前后视图、区域命名稳定性、强度着色、点击回调、深浅主题、中文标签、桌面打包。
- 若区域 ID 与 `muscle_heatmap_json.regions[].id` 无法建立稳定映射，则保留其 SVG 素材并在本地封装渲染层，不把业务模型绑定到第三方 API。
- React Native 方案不适合当前原生 HTML 技术栈；React 专用库也不应作为首选。

参考：

- https://github.com/vulovix/body-muscles
- https://developer.garmin.com/fit/overview/

## 8. API View Model

`get_activity_detail()` 对于已结构化的力量训练，必须返回：

```json
{
  "detail": {
    "detail_surface_mode": "strength",
    "primary_visual": "strength_muscle_map",
    "split_section": "strength_sets",
    "overview_capabilities": {
      "has_track_visual": false,
      "has_laps": false,
      "has_structured_sets": true,
      "has_swim_lengths": false,
      "has_power": false,
      "has_cadence": false,
      "has_hr": true,
      "has_weather": false
    },
    "overview_metrics": [
      { "field": "duration_sec" },
      { "field": "strength_exercise_count" },
      { "field": "strength_working_set_count" },
      { "field": "strength_total_reps" },
      { "field": "strength_total_volume_kg" },
      { "field": "avg_hr" }
    ],
    "strength": {
      "summary": {},
      "exercises": [],
      "muscle_heatmap": {}
    }
  }
}
```

力量活动还必须返回后端事实状态：

```json
{
  "detail": {
    "strength_materialization": {
      "status": "pending|materialized|unstructured|source_missing|failed",
      "version": 1,
      "reason": null
    }
  }
}
```

- `pending` 只表示等待后台物化，不能映射成“设备未提供结构化动作组数据”。
- `unstructured` 才允许使用设备无结构化组的受限说明。
- `source_missing/failed` 使用各自事实文案，不暴露文件路径、堆栈或内部错误。
- `materialized` 才能声明 `has_structured_sets=true`；详情仍只读数据库 JSON。

实现前需要同步更新：

- `docs/js_api_contract.json`
- `docs/运动详情页多运动升级契约摘要.md`
- `metrics_registry.py`
- 对应契约测试

不能仅改前端以绕过既有 `strength_limited` 合同。

## 9. 前端实现规则

### 9.1 新渲染分支

在 `renderActivityDetail()` 中以 `detail.primary_visual === "strength_muscle_map"` 进入专用渲染路径。

该路径必须：

- 隐藏既有 `.overview-track-area` 的轨迹元素，不复用其固定宽高。
- 隐藏圈速/分段表及非户外侧栏。
- 渲染 `strength-overview-layout`、`strength-muscle-map` 和 `strength-sets-table`。
- 只消费后端 `detail.strength`，不在浏览器计算训练容量或热度。
- 处理动作标题、数字和单位的 HTML 转义。

### 9.2 空态

| 条件 | 页面结果 |
| --- | --- |
| `has_structured_sets=false` | 保持当前 `strength_limited` 基础摘要和数据边界文案 |
| `strength_materialization.status=pending` | 显示“正在补全力量训练数据”，不得显示设备无数据；允许有界刷新详情状态 |
| `strength_materialization.status=source_missing` | 显示源数据暂不可用，不猜测动作或肌群 |
| `strength_materialization.status=failed` | 显示数据处理未完成，可在后端重试；不展示内部错误 |
| `strength_materialization.status=unstructured` | 明确说明 FIT 未提供有效结构化动作组 |
| 有训练组，无可映射肌群 | 显示动作表和基础指标；肌肉图显示“已记录动作暂未建立肌群映射” |
| 有部分映射 | 显示热力图与覆盖率提示；未映射动作仍展示 |
| 有重量缺失 | 显示动作和次数；总训练容量显示已知重量部分，不补算缺失重量 |
| 详情数据异常 | 清空旧活动的热力图、动作表与选中状态，显示详情加载失败 |

### 9.3 可访问性

- 前/后人体均提供可读名称与可聚焦的区域说明。
- 色阶必须配合文字等级与悬停信息，不能仅靠颜色传达强度。
- 动作表使用语义化 `table`，数值右对齐。
- 图例与“训练分布而非疲劳”说明在可见位置。

## 10. 分阶段任务

### ST-01：真实 FIT 样本与解析探针

目标：

- 收集至少 3 份 Garmin Strength FIT：完整重量、部分重量、自重/未知动作。
- 输出原始消息键、字段可用率和动作标题关联规则。
- 不改产品 UI。

验收：

- 新增脱敏 fixture 或受控的解析快照。
- 测试证明能区分无 `set_mesgs` 与有结构化训练组。

### ST-02：规范化与持久化

目标：

- 在导入/同步阶段将结构化训练组写入活动数据。
- 加入 schema migration、重导入幂等和删除清理。

验收：

- 详情 API 不读取 FIT raw。
- `strength_sets_json`、`strength_summary_json`、`muscle_heatmap_json` 可稳定读取。
- 未结构化活动不生成虚假的空数组事实。

### ST-03：动作肌群映射

目标：

- 建立 `strength_muscle_map_v1`。
- 生成热力图 regions、覆盖率和未映射计数。

验收：

- 映射仅消费规范化动作。
- 未识别动作不会污染肌肉图。
- 热度、总容量和视觉等级的计算均由后端完成。

### ST-04：后端详情合同

目标：

- 将已结构化力量训练切换到 `strength_muscle_map / strength_sets`。
- 扩展概览指标字段与 `detail.strength` payload。

验收：

- 所有旧力量训练仍保持 `strength_limited`。
- `has_structured_sets` 只在真实结构化数据存在时为 `true`。

### ST-05：前端与人体图 POC

目标：

- 完成开源人体图的本地集成验证。
- 实现宽尺寸的前后人体图、基础指标和动作表。

验收：

- 不继承 260px 轨迹尺寸。
- 1024px 以上双人体并排，760px 以下视图切换。
- 鼠标、键盘和触摸均可完成肌肉与动作联动。

### ST-06：回归、视觉验收与文档闭环

目标：

- 覆盖数据、布局、空态、迁移和既有非力量详情回归。
- 更新多运动合同与完成报告。

验收：

- 跑步、骑行、游泳、恢复类和无结构化力量活动不回归。
- 深色主题下人体分区、文字和表格不重叠、不溢出。

### ST-07：历史物化合同与候选扫描

目标：

- 冻结物化版本、状态和安全候选合同。
- 提供只读 dry-run，证明历史结构化 FIT 不再被当作普通未变化文件跳过。

### ST-08：版本化后台回填

目标：

- 实现异步、限批、幂等的力量物化 worker。
- 只更新力量 JSON 与物化状态，不改其他活动事实。

### ST-09：同步去重与回填一致性

目标：

- 让本地同步、手动导入和远端同步识别缺失/过期物化状态。
- 保持普通 FIT 的快速跳过和所有既有去重语义。

### ST-10：详情状态与受限文案

目标：

- 区分 pending、unstructured、source_missing 和 failed。
- 后台完成后通过有界刷新进入真实热力图，不在详情路径解析 FIT。

### ST-11：真实数据验收与闭环

目标：

- 在自动化全绿后先对真实数据库 dry-run；经用户确认并完成一致性备份后执行生产回填。
- 用真实活动详情验证动作、组、重量、容量和肌肉图，再更新完成报告。

### ST-12：非户外详情模块清理与动作中文展示

目标：

- 修复截图验收偏差：结构化力量页右侧动作名使用中文展示。
- 修复标准概览容器残留：力量热力图页不得再露出轨迹缩略图、圈速统计或赛事照片面板。
- 将同一规则推广到有氧、恢复、泛训练等所有非户外详情页。

验收：

- 已知动作的中文展示来自后端 view model，前端不做翻译和猜测。
- `strength_muscle_map` 独立布局通过 CSS hidden 防护真正替代标准概览布局。
- `primary_visual != track_map` 时隐藏轨迹主视觉区域。
- `split_section` 不是 `laps`、`indoor_segments` 或 `swim_lengths` 表格合同时隐藏分段区；
  其中 `laps` 仅允许 `endurance_outdoor` 使用。
- 户外耐力活动原有轨迹缩略图、圈速表和赛事照片不回归。

## 12. 完成定义

以下条件全部满足才可称“力量训练概览页已交付”：

1. 至少一份真实 Garmin Strength FIT 能端到端展示动作、组数、次数、重量与肌肉图。
2. 所有动作、组数、重量和肌群均可追溯至 FIT 结构化消息或受版本控制的动作映射表。
3. 无结构化动作数据的力量活动不会出现任何猜测性训练结论。
4. 肌肉图不受现有轨迹缩略图 260px 尺寸约束，桌面端前后视图清晰可读。
5. 动作表和肌肉图对部分数据、未知动作、缺失重量都有正确降级。
6. 现有多运动详情合同、数据库迁移、自动化测试和视觉验收全部通过。
7. 历史结构化力量活动无需用户手动重导入即可完成物化；详情页不得长期停留在错误受限态。
8. pending、unstructured、source_missing、failed 四种状态在 API 和前端有不同且事实准确的表达。
9. 本地同步不会因 mtime/size 未变化而跳过缺失或过期的力量物化，同时普通活动性能不回归。
10. 至少一份真实历史活动经 dry-run 与用户批准后的生产回填，能端到端展示动作、组数、重量、
    容量和肌肉图；生产执行前已完成一致性数据库备份与恢复检查。
