## 1. 升级目标

运动详情页不能继续把跑步和骑行的页面结构直接套到所有活动类型上。

本次升级目标是：

- 概览 Tab 根据运动类型展示真正有意义的指标和模块。
- 复盘 Tab 根据运动类型进入不同分析模式，无法分析时明确降级。
- 前端不再用本地 sport 字符串矩阵作为权威。
- AI 只解释后端 snapshot 中已经给出的事实、状态和能力，不补运动事实。
- 力量训练、瑜伽、普拉提、呼吸、室内有氧等非户外运动不再出现跑步式配速、路线、爬升、撞墙等错位叙事。

一句话原则：

```text
运动详情不是跑步详情的换皮，而是这项运动的数据证据板。
```

## 2. 当前实现基线

### 2.1 已有真理源

当前代码已经具备以下关键基础：

| 能力 | 当前真理源 | 说明 |
| --- | --- | --- |
| 复盘 sport 归一化 | `metrics_registry.py` | `normalize_review_sport_type()` |
| 复盘模式 | `metrics_registry.py` | `get_review_mode()` |
| 复盘能力 | `metrics_registry.py` | `get_review_capabilities()` |
| 详情页圈速列 | `main.py` | `resolve_detail_lap_columns()` |
| 活动详情 API | `main.py` | `Api.get_activity_detail()` 返回 `record` |
| 复盘 API | `main.py` | `Api.get_fatigue_review()` 返回后端 snapshot |
| 复盘 AI prompt | `llm_backend.py` | `build_fatigue_review_messages()` |
| 详情页前端 | `track.html` | `renderActivityDetail()`、`switchDetailTab()`、复盘渲染函数 |

### 2.2 当前复盘模式矩阵

`metrics_registry.py` 当前将活动归入：

| review_mode | 当前覆盖 |
| --- | --- |
| `running` | `running`、`trail_running`、`treadmill_running` |
| `cycling` | `cycling`、`road_cycling`、`mountain_biking`、`indoor_cycling`、`e_biking` |
| `swimming` | `swimming`、`lap_swimming`、`open_water` |
| `general` | `hiking`、`mountaineering`、`walking`、`stand_up_paddleboarding` |
| `not_applicable` | `cardio`、`training`、`strength_training`、`breathing`、`yoga`、`pilates`、`hiit`、`flexibility_training`、`stair_climbing`、`driving`、`generic`、`unknown` |

这说明「复盘类型」已经有后端真理源，但它还不足以驱动完整详情页。详情页还需要一个更细的展示能力层。

### 2.3 当前明显缺口

| 缺口 | 现状风险 | 目标修复 |
| --- | --- | --- |
| 概览 Hero 指标仍主要靠前端 `HERO_FIELD_REGISTRY` | 非户外运动容易显示距离、配速、轨迹等不适用字段 | 后端输出 `detail.overview_blocks` 或同等 view model |
| 轨迹卡按 `caps.has_gps` 隐藏，但空态文案仍偏轨迹分析 | 室内训练用户看到“无法生成轨迹地图”会误解为失败 | 按运动类型显示正确空态或替代模块 |
| `track.html` 的图表 lane 模式仍有本地 `_fatigueReviewChartSportMode()` | 可能与后端 `review_mode` 不一致 | 图表也消费后端 `review_mode/capabilities` |
| `getFatigueReviewSportCopyGroup()` 对 `swimming/general` 有历史 fallback | 游泳可能落到徒步文案组 | 改为后端驱动的文案 profile |
| 力量训练只识别 sport 类型，未解析结构化动作组 | 不能做动作、肌群、总训练量的可靠复盘 | 无 `set_mesgs` 等结构化数据前只做受限概览和空态复盘 |
| AI 对 `not_applicable` 目前降级到 general | 可能对力量、瑜伽生成泛耐力复盘 | 引入不可复盘/受限复盘 prompt 合同 |

## 3. 架构契约

### 3.1 后端是页面能力真理源

详情页所有模块是否显示、显示什么标题、使用什么指标组，必须由后端 view model 或后端 registry 派生。

允许：

- 前端根据后端 `display_mode`、`blocks`、`capabilities` 渲染。
- 前端保留最低限度兼容 fallback，用于老包或异常数据。

禁止：

- 前端维护一套新的权威 sport 矩阵。
- 前端根据 DOM、曲线、卡片是否存在补算指标。
- 前端把 `not_applicable` 活动强行渲染成跑步/骑行复盘。

### 3.2 Activity/FIT 是唯一事实源

所有展示指标必须可追溯至：

```text
FIT raw
  -> fit_engine.py
  -> canonical activities row / MetricsResolver
  -> backend view model
  -> frontend render
```

缺失数据只能进入空态，不得用 AI 或前端估算补齐。

### 3.3 复盘与概览分层

概览回答：

```text
这次运动记录了什么？
```

复盘回答：

```text
基于可用证据，这次运动的强度、稳定性、风险或恢复意义是什么？
```

如果某运动类型没有足够证据回答复盘问题，复盘 Tab 必须显示「不适用」或「受限复盘」，而不是套用跑步指标卡。

### 3.4 不引入重架构

本升级不引入：

- 新数据库事实层
- 新微服务
- 云端特征仓库
- AI 写回 canonical 指标
- 大规模重做 `track.html`

优先沿用现有 `metrics_registry.py`、`main.py`、`llm_backend.py`、`track.html`。

## 4. 多运动详情能力矩阵

建议新增一个详情页能力层，命名可选：

```python
detail_surface_mode
```

或扩展现有 `get_review_capabilities()`，但必须保持后端为真理源。

### 4.1 推荐模式

| detail_surface_mode | 适用运动 | 页面核心问题 |
| --- | --- | --- |
| `endurance_outdoor` | 户外跑步、越野跑、公路骑、山地骑、徒步、登山、步行、开放水域 | 路线、距离、时长、强度、地形、环境 |
| `endurance_indoor` | 跑步机、室内骑行、椭圆机、划船机、室内有氧 | 时长、心率、功率/阻力/踏频、强度区间、稳定性 |
| `swim_pool` | 泳池游泳 | 距离、趟数、配速、划频、SWOLF、泳姿 |
| `swim_open_water` | 公开水域 | 距离、轨迹、配速、划频、心率、环境 |
| `strength` | 力量训练 | 时长、动作、组数、负重、训练量、肌群，数据不足时只显示受限概览 |
| `mobility_recovery` | 瑜伽、普拉提、拉伸、呼吸 | 时长、心率压力、恢复负荷、连续性 |
| `skill_session` | 攀岩、滑雪等技能类 | 时长、强度、海拔/次数/技术指标，按数据质量渐进接入 |
| `generic_session` | 未知、泛训练、设备只给心率和热量 | 时长、心率、热量、训练负荷空态 |
| `not_supported` | 驾车、无法识别、明显非运动 | 仅保留文件事实和不可复盘说明 |

### 4.2 每类活动的模块策略

| 模式 | 概览主指标 | 概览模块 | 复盘策略 |
| --- | --- | --- | --- |
| `endurance_outdoor` | 距离、时长、配速/速度、心率、爬升、热量 | 轨迹、圈速、天气、训练收益、环境挑战 | 完整或专项耐力复盘 |
| `endurance_indoor` | 时长、心率、功率/踏频/速度、热量、训练收益 | 强度卡、圈/分段、设备、无轨迹友好空态 | 室内耐力复盘，不讲路线和环境 |
| `swim_pool` | 距离、时长、配速 `/100m`、SWOLF、划频、心率 | 泳段/趟数、泳姿、训练收益 | 游泳专项复盘或受限复盘 |
| `swim_open_water` | 距离、时长、配速、轨迹、心率、划频 | 轨迹、天气、开放水域环境 | 游泳专项复盘，不套跑步 GAP/爬升 |
| `strength` | 时长、心率、热量、组数、总量、动作数 | 动作组、肌群、训练量，缺结构化数据时显示数据不足 | 无结构化动作数据前不做动作/肌群复盘 |
| `mobility_recovery` | 时长、平均心率、热量、恢复压力 | 心率区间、恢复提示、连续性 | 恢复/压力解读，不输出表现提升结论 |
| `skill_session` | 时长、心率、专项次数/爬升/高度 | 专项模块按数据字段接入 | 只做已接入字段的受限复盘 |
| `generic_session` | 时长、心率、热量 | 数据质量说明 | 受限复盘或不适用 |
| `not_supported` | 文件事实、时间、设备 | 不支持说明 | 不开放复盘 |

## 5. 概览 Tab 升级设计

### 5.1 目标结构

概览 Tab 推荐按后端返回的 blocks 渲染：

```json
{
  "detail_surface_mode": "endurance_indoor",
  "overview_blocks": [
    {
      "type": "hero_metrics",
      "items": []
    },
    {
      "type": "primary_visual",
      "variant": "track_map | indoor_intensity | strength_volume | swim_lanes | empty"
    },
    {
      "type": "splits",
      "columns": []
    },
    {
      "type": "context_cards",
      "items": []
    }
  ]
}
```

第一阶段可以不一次性实现通用 block renderer，但后端必须先输出可验证的 `detail_surface_mode` 和 `overview_capabilities`，让前端逐步迁移。

### 5.2 Hero 指标规则

Hero 指标数量建议保持 4 到 6 个，但字段必须按运动类型变化。

| 运动 | Hero 字段建议 |
| --- | --- |
| 户外跑 | 距离、时长、平均配速、平均心率、爬升、热量 |
| 越野跑/徒步/登山 | 距离、时长、爬升、平均心率、移动速度/配速、最高海拔 |
| 户外骑行 | 距离、时长、平均速度、平均心率、平均功率/NP、爬升 |
| 室内骑行 | 时长、平均心率、平均功率、NP、踏频、热量 |
| 跑步机 | 距离、时长、平均配速、平均心率、步频、热量 |
| 泳池游泳 | 距离、时长、配速 `/100m`、SWOLF、划频、心率 |
| 力量训练 | 时长、平均心率、热量、动作数、组数、总训练量 |
| 瑜伽/拉伸/呼吸 | 时长、平均心率、热量、恢复压力、连续性 |
| 泛训练 | 时长、平均心率、热量、设备记录状态 |

### 5.3 主视觉规则

| 条件 | 主视觉 |
| --- | --- |
| 有 GPS 且 outdoor | 轨迹缩略图 |
| 无 GPS 但为室内耐力 | 强度时间条或心率/功率迷你图 |
| 力量训练且有结构化 set 数据 | 训练量/肌群摘要 |
| 游泳有泳段数据 | 泳段摘要 |
| 数据不足 | 友好空态，说明这类运动不需要轨迹 |

室内运动不得显示「无法生成轨迹地图」作为主要空态。应显示：

```text
这是一条室内运动记录，本次不需要轨迹地图。可查看时长、心率、功率或训练负荷等记录。
```

### 5.4 圈速/分段规则

现有 `detail.lap_columns` 已由后端决定，继续沿用，但要扩展语义：

| 运动模式 | 分段名称 | 列策略 |
| --- | --- | --- |
| 跑步/骑行/徒步 | 圈速统计 | 沿用现有 `lap_columns` |
| 室内骑行 | 分段统计 | 平均功率、NP、踏频、心率、用时 |
| 泳池游泳 | 泳段统计 | 趟数、距离、配速、SWOLF、泳姿 |
| 力量训练 | 动作组 | 动作、组数、次数、负重、容量 |
| 恢复类 | 心率区间 | 时长、平均心率、热量 |
| 数据不足 | 记录摘要 | 说明设备未提供可分段数据 |

## 6. 复盘 Tab 升级设计

### 6.1 复盘模式不等于详情模式

`review_mode` 当前是复盘引擎模式，应继续保留。建议新增更细的：

```json
{
  "review_profile": "endurance_outdoor | endurance_indoor | swim | strength_limited | recovery_limited | generic_limited | not_applicable"
}
```

`review_mode` 保持兼容：

- `running`
- `cycling`
- `swimming`
- `general`
- `not_applicable`

`review_profile` 用于 UI 和 AI 文案分流。

### 6.2 复盘页面类型

| review_profile | 复盘页面 |
| --- | --- |
| `endurance_outdoor` | 当前完整复盘驾驶舱，保留曲线、事件、疲劳带 |
| `endurance_indoor` | 室内强度复盘，隐藏路线/爬升/天气压力，突出心率、功率、踏频、稳定性 |
| `swim` | 游泳专项复盘，突出配速、SWOLF、划频、心率和持续性 |
| `strength_limited` | 力量受限复盘，结构化数据不足时只显示时长/心率/负荷空态 |
| `recovery_limited` | 恢复类复盘，强调压力和恢复，不做表现评价 |
| `generic_limited` | 泛训练受限复盘，只解释已记录的心率、时长、热量 |
| `not_applicable` | 不开放复盘，说明原因 |

### 6.3 指标卡替换原则

当前复盘 Tab 有 8 张指标卡。升级后不要求所有运动都显示 8 张卡。

| 模式 | 指标卡建议 |
| --- | --- |
| 跑步 | 心率漂移、后程效率、能量风险、状态下滑点、运动效率、耐久、步频稳定、训练负荷 |
| 骑行 | 输出节奏、功率效率、后程功率保持、状态下滑点、心肺对照、踩踏组织、相对强度、能量风险 |
| 室内骑行 | 输出节奏、心肺对照、踩踏组织、相对强度、训练负荷 |
| 跑步机 | 心率漂移、后程效率、步频稳定、训练负荷，不显示地形/GAP |
| 游泳 | 配速稳定、SWOLF 趋势、划频稳定、心率负荷、持续性 |
| 力量训练 | 训练量、动作覆盖、组间结构、心率压力，结构化数据缺失时显示不可判断 |
| 恢复类 | 时长完成度、心率压力、恢复负荷、连续性 |
| 泛训练 | 时长、心率、热量、训练负荷空态 |

前端可在第一阶段先保持 DOM 槽位，但必须允许某些卡片隐藏或显示「不适用」，不能用跑步文案填满。

### 6.4 曲线和图表规则

| 模式 | 曲线 |
| --- | --- |
| 户外跑/越野 | 心率、配速、GAP、效率、海拔、坡度、地形负荷 |
| 户外骑行 | 功率、心率、海拔、踏频、坡度、地形负荷 |
| 室内骑行 | 功率、心率、踏频、速度或阻力，禁止海拔/坡度空图 |
| 跑步机 | 心率、配速、步频，禁止路线/地形负荷 |
| 游泳 | 配速、心率、划频、SWOLF |
| 力量训练 | 动作组/训练量时间线，缺结构化数据时不画 |
| 恢复类 | 心率区间或时长条 |

图表 lane 选择必须消费后端返回的 `review_mode`、`review_profile` 或 `capabilities`，不得继续只读 `sport_type`。

### 6.5 不适用页面

当 `review_mode=not_applicable` 或 `capabilities.is_applicable=false` 时，复盘 Tab 显示：

```text
这类运动暂不适合使用耐力复盘。
本次可查看概览中的时长、心率、热量和设备记录；若后续设备提供动作组、泳段或专项结构化数据，脉图会开放专项复盘。
```

并显示可用事实：

- 时长
- 平均心率
- 热量
- 设备
- 数据质量

不得显示：

- 能量断档风险
- GAP
- 后程效率
- 步频稳定性
- 路线/爬升推断
- 肌群热图推断

## 7. 后端合同

### 7.1 推荐新增字段

在 `record.detail` 中新增：

```json
{
  "detail_surface_mode": "strength",
  "overview_capabilities": {
    "has_track_visual": false,
    "has_laps": false,
    "has_structured_sets": false,
    "has_swim_lengths": false,
    "has_power": false,
    "has_cadence": false,
    "has_hr": true,
    "has_weather": false
  },
  "overview_empty_states": {
    "primary_visual": "indoor_no_track",
    "splits": "structured_sets_missing"
  }
}
```

在 `get_fatigue_review()` snapshot 顶层新增：

```json
{
  "review_profile": "strength_limited",
  "not_applicable_reason": "structured_strength_data_missing",
  "available_review_facts": ["duration", "avg_hr", "calories"]
}
```

### 7.2 Registry 扩展建议

在 `metrics_registry.py` 中扩展能力注册，不建议新建平行文件：

```python
DETAIL_SURFACE_MODE_SPORTS = {
    "endurance_outdoor": frozenset({...}),
    "endurance_indoor": frozenset({...}),
    "swim_pool": frozenset({...}),
    "strength": frozenset({...}),
    "mobility_recovery": frozenset({...}),
}
```

提供函数：

```python
get_detail_surface_mode(sport_type)
get_detail_capabilities(sport_type)
get_review_profile(sport_type, capabilities)
```

要求：

- `normalize_review_sport_type()` 继续作为归一化入口。
- 不得让 unknown 默认归入 running。
- `indoor_cycling` 可以 `review_mode=cycling`，但 `detail_surface_mode=endurance_indoor`。
- `treadmill_running` 可以 `review_mode=running`，但 `detail_surface_mode=endurance_indoor`。
- `strength_training` 必须区分 `sport recognized` 和 `structured strength parsed`。

### 7.3 力量训练数据边界

当前 FIT 解析路径主要覆盖 session、lap、record 级数据。力量专项需要的结构化消息包括但不限于：

- `set_mesgs`
- `exercise_title_mesgs`
- `workout_step_mesgs`

在没有解析这些消息前：

- 不做肌群热图。
- 不推断动作名称。
- 不推断训练量。
- 不输出动作结构复盘。
- 只显示受限概览和「设备未提供结构化力量数据」空态。

### 7.4 API contract 同步

新增字段必须同步到：

- `docs/js_api_contract.json`
- `tests/test_response_envelope_contract.py`
- 复盘白名单相关测试
- 详情页前端测试

## 8. 前端合同

### 8.1 概览渲染

第一阶段最小改造：

- `_resolveHeroItems(record)` 优先消费 `record.detail.overview_metrics` 或 `record.detail.detail_surface_mode`。
- `renderActivityDetail()` 的轨迹区域按 `overview_capabilities.has_track_visual` 决定。
- 无轨迹室内运动显示室内空态，不显示轨迹失败。
- 圈速表标题按 `detail_surface_mode` 改为「圈速统计 / 分段统计 / 泳段统计 / 动作组 / 记录摘要」。

### 8.2 复盘渲染

必须修改：

- `_fatigueReviewChartSportMode()`：优先读取后端 `review_mode` 或 `review_profile`。
- `_fatigueReviewChartLaneDefs()`：按后端能力选择 lane。
- `_fatigueReviewMetricCardDefs()`：允许按 `review_profile` 返回不同卡片集合。
- `_renderFatigueReviewSummary()`：当 `not_applicable` 时显示不适用摘要，不渲染跑步/骑行指标。
- `getFatigueReviewSportCopyGroup()`：不得把 `swimming` fallback 到 `hiking`，不得把 unknown fallback 到 running 作为权威。

### 8.3 UI 文案边界

用户可见文案必须是产品语言，不暴露：

- `not_applicable`
- `review_mode`
- `unsupported_sport`
- `structured_strength_data_missing`
- `missing_power`
- `records<20`

可显示：

- 当前运动类型暂不适合耐力复盘
- 设备没有提供足够动作组数据
- 功率数据不足，暂不判断输出稳定性
- 本次为室内运动，不需要轨迹地图

## 9. AI 合同

### 9.1 Prompt 分流

`llm_backend.build_fatigue_review_messages()` 必须读取：

- `snapshot.review_mode`
- `snapshot.review_profile`
- `snapshot.capabilities`
- `snapshot.not_applicable_reason`

当 `review_profile` 为 `strength_limited`、`recovery_limited`、`generic_limited` 或 `not_applicable`：

- 不输出完整耐力复盘。
- 不提 GAP、爬升、路线、撞墙、后程效率。
- 不把瑜伽/拉伸写成训练表现提升。
- 不为力量训练生成动作、肌群、负重结论。

### 9.2 输出要求

受限复盘仍可输出结构化 JSON，但内容必须围绕：

- 数据是否足够
- 本次记录可解释的事实
- 不可解释的边界
- 下一次如何让设备记录更完整

### 9.3 禁止行为

AI 不得：

- 依据运动标题猜动作或肌群。
- 依据热量猜训练强度区间。
- 依据心率猜功率。
- 依据无 GPS 室内记录猜路线。
- 把 `not_applicable` 活动当 `general` 耐力运动讲。
