# 轨迹分析工具轨迹加载性能优化任务清单

本清单处理高密度运动轨迹加载超过 5 秒的问题，当前已用“四姑娘山二峰登顶”和“长坪沟到四姑娘山二峰大本营徒步”作为基线样本。优化目标是缩短用户从选择活动到地图、指标和剖面可用的等待时间，同时保留轨迹事实、CP 编辑、里程、最高点 / 坡顶、进度切片、剖面联动和相机行为。

## 0. 当前证据与根因结论

### 0.1 样本规模

| 活动 | activity id | 点数 | track JSON 大小 | 后端 `load_activity_track` 本地耗时 |
| --- | ---: | ---: | ---: | ---: |
| 四姑娘山二峰登顶 | `127` | `26,052` | 约 `9.3 MB` | 约 `0.07s` |
| 长坪沟到四姑娘山二峰大本营徒步 | `907` | `21,690` | 约 `7.9 MB` | 约 `0.05s` |

后端本地读取不是当前 5 秒级等待的首要证据；仍需在真实 DMG 中补充分段计时，不能把本地探针耗时直接当成 WebView bridge 耗时。

### 0.2 高置信性能热点

- `jumpToTraceFromActivityDetail()` 等待 `load_activity_track()` 返回完整 points，再进入同步的 `applyDataAndRender()`。
- `applyDataAndRender()` 在首屏路径中依次执行统计、marker 检测、边界扫描、`updateScene()`、剖面图 / ECharts、固定 `2.5s` `camera.flyTo()`、全量 `JSON.stringify(appState.points)` 的 `sync_track_context()` 和报告 / 列表渲染。
- `_buildStatsFromCanonical()` 即使点上已有 `dist_km`，仍会对每一对相邻点无条件执行 `haversine()`，只是随后优先使用已有距离值。
- `haversine()` 每次调用都会执行一次 `console.warn()`；canonical 距离循环和峰顶邻域扫描会在高密度轨迹上产生大量重复日志，这是应优先处理的高置信主线程热点。
- `_detectPeakMarkers()` 对每个候选点向前、向后扫描 300 米邻域，并反复执行三角函数距离计算；高密度轨迹上成本随点数和局部采样密度增长。
- `updateScene()` 为全量 points 创建 Cesium `Cartesian3`，再重建完成 / 未完成轨迹 entity；真实地形下 `clampToGround` 会把这一批顶点交给 terrain 渲染链路。
- `syncCurrentTrackContextForActivityAdvice()` 在 canonical activity 场景仍将完整 points 再次 `JSON.stringify` 并跨 pywebview bridge 发送，造成重复序列化和大 payload 传输。
- 真实地形场景另外包含 `ArcGISTiledElevationTerrainProvider.fromUrl()`、最多约 `1200ms` 的 terrain settle 等待、三帧稳定判定和 `World_Shaded_Relief` imagery overlay 首次瓦片请求；它们必须与普通轨迹加载单独计时。

## 1. 冻结产品和事实边界

- FIT / 手表 points 与后端 canonical metrics 仍是唯一活动事实源。
- 不用轨迹抽稀结果重写距离、爬升、最高海拔、复盘、AI 或数据库事实。
- 保留 CP 展示、新增、编辑、删除和侧栏联动。
- 保留 1km / 5km / 10km 里程层级、开关和真实 `dist_km` 来源。
- 保留最高点优先于普通坡顶的层级、开关和 declutter 语义。
- 保留完成 / 未完成轨迹切片、进度滑块、底部海拔剖面图及点击联动。
- 保留 2D / 3D slider 只控制视角、标准 / 真实地形按钮只控制 terrain provider 的职责分工。
- 保留 CDEM-12 已达到可接受程度的 DMG 相机行为，不以性能修复重新引入 framing 跳变。
- DEM、hillshade、海拔墙、MapLibre / deck.gl、FIT / GPX、DB、活动详情 / 复盘和 AI 语义不是本任务的重做范围。

## 2. 量化门禁

| 项目 | 门禁 |
| --- | --- |
| 首屏可用 | 高密度轨迹的地图主体、顶部指标和底部剖面先达到可操作状态；不得等待非关键报告或背景同步 |
| 分段耗时 | 必须记录 bridge、JSON decode、统计、峰顶检测、Cesium entity、图表、相机和背景同步各段耗时 |
| 性能目标 | 以 PLOAD-00 真实 DMG 基线冻结；修复后首屏交互等待至少下降 `30%`，不得用未测量的主观感觉替代 |
| 语义 marker | CP、1/5/10km、最高点 / 坡顶的数量、优先级、编辑和开关合同不变 |
| 轨迹视觉 | 不因视觉抽稀造成明显路线形状偏移；抽稀只允许用于 Cesium 显示几何，原始 points 保留 |
| 相机 | 不新增路线重新 fit；保留当前 slider、heading / pitch / range 语义和 DMG 可接受体验 |
| 真实地形 | 普通标准地形加载不等待 DEM；真实地形额外网络时间单独显示和验收 |
| 失败回退 | provider、hillshade 或后台优化失败不得阻断标准轨迹分析工具 |

## 3. 执行规则

- 每项任务开始前刷新 CDEM 契约摘要并落盘该子任务工程级提示词。
- 当前任务测试全绿并通过 adaptive diff review 后，才能进入下一项。
- 首项必须先测量，禁止先改 `flyTo` 时长、抽稀比例、峰顶算法或 bridge payload。
- 优先顺序固定为：热循环与逐次日志、canonical 重复传输、相机与非关键任务调度；只有复测仍未达标时才进入 Cesium 显示几何抽稀。
- PLOAD-01 至 PLOAD-03 完成后必须执行中期性能复测；如已达到性能目标，PLOAD-04 以“无需引入显示抽稀”的证据结论完成，不得为完成清单强行增加双轨迹结构。
- 任何性能优化都必须保留原始 points，并以同一路线对比语义 marker 和剖面事实。
- 工作区已有大量 dirty 修改，不得 stash、reset、覆盖或格式化无关文件。
- 如性能优化触及数据/API 生命周期、事实字段、provider 语义或相机合同，必须重新全文阅读交付手册、主任务清单、契约摘要和相关源码 / 测试。

## 5. 任务详情

### PLOAD-00：加载链路分段基线

状态：`Completed`　优先级：P0　性质：审计 / 测量 / 不改变生产行为

目标：在真实 DMG 和本地开发环境中拆出 5 秒等待的实际来源。

必做：

- 记录 `load_activity_track` 后端耗时、返回 payload 字节数、pywebview bridge 往返耗时和 JS decode 耗时。
- 在 `applyDataAndRender()` 记录 stats、峰顶、bounds、`updateScene`、profile、ECharts、`flyTo` 启动、`sync_track_context` 和报告渲染耗时。
- 覆盖 activity `127`、`907`、普通城市跑、普通骑行；至少覆盖标准地形和真实地形两条路径。
- 区分首次 Cesium 初始化、首次活动加载、同一窗口第二次加载和切换 DEM 后加载。
- 记录点数、JSON 大小、km marker 数量、peak marker 数量、曲线长度和首个可交互时间。

允许修改：诊断脚本、临时测试夹具、文档；不改变生产行为，不把临时计时器直接作为最终产品日志。

验收：聚焦测试、基线报告、`git diff --check`；未执行的 DMG 或网络场景不得写成通过。

完成标准：至少确认两个主要瓶颈，并冻结后续任务的输入指标。

完成记录：

- 新增 `scripts/profile_track_load.py`，只读加载 activity `127` / `907`，执行当前 `track.html` 的 `haversine()`、`_detectPeakMarkers()` 和 `_buildStatsFromCanonical()` 源码并输出结构化基线。
- 确认 activity `127` 前端 stats / peak 探针约 `536.802ms`、`21,140,328` 次 `console.warn()`；activity `907` 约 `220.093ms`、`8,764,412` 次 `console.warn()`。

- 已启动打包 `脉图.app` 并进入轨迹分析工具；用户 DMG 观察到四姑娘山活动约 5 秒以上，精确 WebView / Cesium / DEM 分段仍待后续真实 UI 计时。
- 验证通过：`20 passed`、`git diff --check`；基线报告：`docs/轨迹分析工具_Cesium_DEM_POC_轨迹加载性能_PLOAD_00_基线报告.md`。

### PLOAD-01：热循环、逐次日志与峰顶检测优化

状态：`Completed`　优先级：P0　前置：PLOAD-00

目标：先消除 canonical 首屏路径上确定性强、风险低的 CPU 和日志热点。

必做：

- 将 `haversine()` 的逐次 `console.warn()` 删除或改为一次性诊断；热循环内不得产生逐点 console 输出。
- 当 points 已包含有效 `dist_km` 时，不再为 fallback 距离无条件计算相邻 haversine。
- 将峰顶检测改为线性 / 有界窗口实现，或复用后端已 materialize 的视觉候选事实；不得改变最高点优先级和 300 米语义边界，除非有对比报告与明确批准。
- 对 activity `127`、`907` 和普通路线比较 marker 数量、最高点位置、普通坡顶位置和完成时间。
- 预览路径可以继续计算距离，但不得影响 canonical activity 首屏路径。

允许修改：`track.html`、必要的后端视觉候选字段、聚焦测试和文档。

禁止：用抽稀点重算活动距离、爬升、最高海拔或复盘 / AI 事实；禁止删除最高点 / 坡顶功能。

完成标准：canonical 热路径不再产生逐点日志或冗余距离计算；算法耗时有基线对比；marker 语义和位置回归通过。

完成记录：

- activity `127` / `907` stats / peak 探针分别下降约 `68.3%` / `61.5%`，warning count 从 `21,140,328` / `8,764,412` 降为 `0`。
- 城市跑 activity `1117` 和骑行 activity `1094` 分别下降约 `66.3%` / `38.7%`。
- 四条真实轨迹的 peak 数量、经纬度、海拔、最高点标志和 km marker 数量均保持一致。
- 验证通过：`22 passed`、JS 语法、`git diff --check`；完成报告：`docs/轨迹分析工具_Cesium_DEM_POC_轨迹加载性能_PLOAD_01_完成报告.md`。

- 验证通过：`41 passed`、JS 语法、`git diff --check`；完成报告：`docs/轨迹分析工具_Cesium_DEM_POC_轨迹加载性能_PLOAD_03_完成报告.md`。

### PLOAD-05：真实 DEM 加载性能隔离

状态：`Completed`　优先级：P1　前置：PLOAD-03

目标：分离普通轨迹加载和用户主动选择真实地形后的网络 / terrain settle 成本。

必做：

- 分别记录 provider metadata、首批 terrain tile、`tilesLoaded` settle、hillshade imagery 和 marker 重建耗时。
- 标准地形加载不等待 DEM、hillshade 或 terrain settle。
- 真实地形失败时不阻断标准地图和轨迹分析交互。
- 不引入长期缓存，不改变用户退出即清理的 DEM 策略。

完成标准：报告明确普通加载与真实地形加载各自耗时，且失败回退合同保持通过。

完成记录：
