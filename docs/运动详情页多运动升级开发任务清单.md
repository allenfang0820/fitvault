# 脉图运动详情页多运动升级开发任务清单

本文档把 `docs/运动详情页多运动升级开发交付手册.md` 拆为可独立执行、验证、提交和回归的工程任务。

本轮目标是让活动详情页的「概览」和「复盘」按运动证据展示，而不是将跑步或骑行页面套给所有活动。重点覆盖室内骑行、跑步机、泳池游泳、力量训练、瑜伽/拉伸/呼吸、泛训练和未知类型。

## 0. 执行规则

- 唯一产品和工程基线是 `docs/运动详情页多运动升级开发交付手册.md`。
- 每个任务开始前执行 `git status --short`，阅读将要修改文件的既有 diff。
- 当前工作区可能包含其他发布或 ACS 任务改动；不得 stash、reset、覆盖、格式化或提交无关改动。
- 每个任务只修改“允许改动文件”列出的范围。发现必须扩大范围时，先更新本清单和对应合同。
- 首次任务前必须全文阅读交付手册、本清单和项目契约，并落盘 `docs/运动详情页多运动升级契约摘要.md`。后续每项任务开始前先刷新该摘要、记录工程级执行提示词；仅当目标或合同发生严重偏离时才重新全文阅读上述源文档。
- `metrics_registry.py` 是运动类型、详情展示模式和复盘能力的唯一真理源。前端不得新增第二套权威 sport 矩阵。
- 前端只消费后端字段，不从 DOM、ECharts、曲线或空态文字补算事实。
- AI 只解释 snapshot 已给出的事实、状态和能力；不得猜动作、肌群、功率、路线或环境。
- 力量训练在未解析 `set_mesgs`、`exercise_title_mesgs`、`workout_step_mesgs` 前，只能进入受限概览或数据不足状态。
- 每个任务结束后运行聚焦测试、`git diff --check`，并确认新增字段已同步到 `docs/js_api_contract.json`。
- 除 `MDT-07` 外，各任务都应能单独提交；不要把 UI、后端合同和 AI 分流压成一个不可回滚的大提交。

## 4. MDT-01：后端运动能力 Registry 扩展

优先级：P0  
状态：`Planned`  
性质：后端单一真理源  
前置：MDT-00

### 目标

在现有 `metrics_registry.py` 的 review registry 基础上，输出详情展示模式和复盘 profile，消除前端、图表、AI 各自维护 sport 分支的风险。

### 允许改动文件

- `metrics_registry.py`
- `tests/test_fatigue_review_sport_capability_registry.py`
- `tests/test_activity_detail_multi_sport_capabilities.py`
- `docs/js_api_contract.json`
- 本任务清单和交付手册中的合同段落

### 必做

- 新增 `DETAIL_SURFACE_MODE_SPORTS` 或等价后端注册表。
- 新增 `get_detail_surface_mode(sport_type)`。
- 新增 `get_detail_capabilities(sport_type)`。
- 新增 `get_review_profile(sport_type, capabilities)`。
- 保持现有 `normalize_review_sport_type()`、`get_review_mode()`、`get_review_capabilities()` 的兼容语义。
- 明确以下关键路由：
  - `treadmill_running`：`review_mode=running`，`detail_surface_mode=endurance_indoor`，`review_profile=endurance_indoor`。
  - `indoor_cycling`：`review_mode=cycling`，`detail_surface_mode=endurance_indoor`，`review_profile=endurance_indoor`。
  - `lap_swimming`：`detail_surface_mode=swim_pool`，`review_profile=swim`。
  - `open_water`：`detail_surface_mode=swim_open_water`，`review_profile=swim`。
  - `strength_training`：`detail_surface_mode=strength`，默认 `review_profile=strength_limited`。
  - `yoga`、`pilates`、`breathing`、`flexibility_training`：`detail_surface_mode=mobility_recovery`，`review_profile=recovery_limited`。
  - `cardio`、`training`、`hiit`：按合同进入 `endurance_indoor` 或 `generic_session`，但必须由记录能力而非前端猜测决定。
  - `driving`、`unknown`：不得进入跑步或骑行，进入 `not_supported` 或 `generic_session`。

## 5. MDT-02：活动详情概览 View Model

优先级：P0  
状态：`Planned`  
性质：详情 API / 后端 view model  
前置：MDT-01

### 目标

让 `get_activity_detail()` 返回足够的、后端决定的多运动展示信息，使前端不必用 `HERO_FIELD_REGISTRY` 猜测展示结构。

- `docs/js_api_contract.json`

### 必做

- 在 `_build_record_from_row()` 的 `record.detail` 中输出：
  - `detail_surface_mode`
  - `overview_capabilities`
  - `overview_empty_states`
  - `overview_metrics`
  - `primary_visual`
  - `split_section`

## 6. MDT-03：概览 Tab 多运动渲染

优先级：P1  
状态：`Planned`

前置：MDT-02

### 目标

## 7. MDT-04：复盘快照 Profile 与受限状态

优先级：P0  
状态：`Planned`  
性质：复盘后端 / snapshot 合同  
前置：MDT-01

### 目标

让 `get_fatigue_review()` 明确输出完整、受限或不适用的复盘状态，避免前端和 AI 将 `not_applicable` 强行当成跑步/骑行/general 耐力复盘。

### 允许改动文件

- `metrics_registry.py`
- `tests/test_fatigue_review_snapshot_realignment.py`
- `tests/test_fatigue_review_quality_gate.py`

- `tests/test_response_envelope_contract.py`
- `tests/test_fatigue_review_ai_preflight_p8.py`
- `docs/js_api_contract.json`

### 必做

- `_build_fatigue_review_snapshot()` 顶层输出：
  - `review_mode`
  - `review_profile`
  - `capabilities`
  - `not_applicable_reason`
  - `available_review_facts`
- `endurance_indoor`：
  - 保留心率、功率、踏频、速度等有事实支撑的字段。
  - 不把海拔、坡度、天气或路线作为默认解释依据。
- `swim`：
  - 只导出已有的配速、SWOLF、划频、心率等事实；没有即明确缺失。
- `strength_limited`：
  - 默认不生成跑步八卡的确定性指标。
  - `available_review_facts` 只列本次真实记录的时长、心率、热量等。

- `recovery_limited` 和 `generic_limited`：
  - 不输出跑步/骑行疲劳事件、GAP、爬升或后程效率结论。
- `not_applicable`：
  - 不构造耐力指标卡输入、曲线或风险事件。

  - 不出现 GAP、爬升、跑步配速或骑行功率推断。
