# 运动生涯加载体验契约摘要

本摘要冻结「运动生涯」加载体验优化的产品、数据、API、缓存和验证边界。它只约束加载编排，不改变 ACS 的事实模型和业务语义。

## 1. 当前基线

- 应用启动默认进入「个人运动数据」；首访说明场景进入「帮助说明」。
- 应用启动不得全量预热运动生涯。
- 切入一级导航「运动生涯」时，才触发生涯首屏加载。
- 当前 `loadCareerData()` 会同时触发多个生涯模块，本轮将其拆为首屏、按需和后台预取三个层次。

## 2. 不可改变的架构契约

1. `Activity` 是唯一事实源。
2. `Resolver` 负责赛事、PB、成就、里程碑等语义判断。
3. `ACS` 只组织派生展示和索引，不复制 raw FIT 或完整 Activity 事实。
4. 前端只消费后端 ViewModel，不根据标题、距离、配速、DOM、图表或缺失值推断事实。
5. 所有可点击生涯对象继续通过 `activity_id` 回跳 Activity Detail。
6. AI 只消费 Career Snapshot / Year Snapshot，不读取原始 FIT、points、track_json、SQLite schema、本地路径或媒体存储路径。
7. pywebview API 既有字段语义和 envelope 不因本轮加载优化而改变；新增字段必须同步 `docs/js_api_contract.json` 与测试。

## 3. 加载分层契约

### 3.1 首屏层

进入运动生涯后，首屏只必须等待：

- 页面壳和总览骨架渲染。
- `get_career_overview`。
- 必要的年度轻量结构；若年度数据可独立延迟，则不得阻塞总览关键事实。

首屏不得等待：

- 完整时间轴。
- 完整赛事档案。
- 记录中心全部分析曲线。
- 足迹地图脚本或地图重绘。
- 相册大图或全部媒体预览。
- 年度 AI 总结生成。

### 3.2 按需层

用户进入子页时才加载对应数据：

| 子页 | 入口数据 | 重数据 |
| --- | --- | --- |
| 时间轴 | 默认筛选的时间轴 ViewModel | 过滤条件变化后的时间轴 |
| 赛事档案 | `get_career_races` | 赛事媒体/详情下钻 |
| 记录中心 | 记录目录与当前记录 | `get_career_record_detail`、`get_career_record_metric_series` |
| 足迹 | 足迹摘要和点位 | 地图脚本、地图重绘 |
| 相册 | 相册列表和白名单预览 | 图片按可见区域加载 |
| AI 总结 | 当前年度/生涯报告状态 | 用户主动触发的生成或重生成 |

### 3.3 后台预取层

- 只在总览完成后、浏览器空闲时调度。
- 优先预取时间轴默认数据和记录中心轻量入口。
- 预取结果必须能被用户主动切页复用。
- 预取失败不得覆盖总览成功状态。
- 不预取地图脚本、相册大图或 AI 生成。

## 4. 状态与缓存契约

每个子模块必须能表达至少以下状态：

```text
idle | loading | loaded | stale | empty | error
```

要求：

- 子模块拥有独立的 loading promise、错误状态和 source version。
- 同一 `careerSourceVersion` 的缓存可直接渲染，不得因切页强制重复请求。
- 数据源变化时，相关模块标记 stale 并后台刷新；已有内容不应被清空。
- 用户当前可见页面的主动加载优先于后台预取。
- 晚到响应不得覆盖更新版本的数据或用户当前页状态。
- 一个子模块失败不得让其他已成功模块回退为全局失败。

## 5. 记录中心特殊边界

- 运动生涯总览不触发记录中心全部分析曲线。
- 记录中心入口先加载目录和当前记录列表。
- 选中具体记录后，才加载详情和指标序列。
- `recordsBySport` 继续按同一 `careerSourceVersion` 复用。
- 切换记录指标不得触发生涯全量刷新。

## 6. 刷新触发契约

以下事件可以触发生涯数据刷新，但必须尽量按受影响模块刷新：

- FIT 导入或同步完成。
- Activity 删除或事实更新。
- 用户切换赛事标记。
- 用户修改赛事档案可编辑元数据。

刷新要求：

- 不影响个人运动数据主流程。
- 不清空未受影响模块的现有内容。
- 刷新失败保留旧内容并显示产品化局部错误态。

## 7. API 与数据契约

- 优先复用现有 API，不为“加载状态”复制一套平行事实 API。
- `get_career_overview_secondary_metrics` 继续作为总览次级指标延迟合并的参考模式。
- 所有新增加载状态字段必须是展示编排字段，不得伪造业务事实。
- 后端仍负责事实、排序、统计和安全字段白名单；前端只负责编排请求和渲染状态。

## 8. 验收红线

完成后必须满足：

- 首次点击运动生涯时，总览关键事实先可见。
- 未打开的重模块不阻塞总览首屏。
- 子页拥有局部 loading / empty / error 状态。
- 重复进入时缓存优先显示，后台刷新不闪屏。
- 时间轴、赛事档案、记录中心、足迹、相册、AI 总结之间互不因单点失败而级联失败。
- 现有 ACS 业务测试、数据边界测试、API envelope 测试和前端渲染测试继续通过。
- Windows 真机、Windows 打包、macOS 打包和真实数据人工验收仍属于后置门禁，不能因本轮代码测试通过而误标完成。

## 9. 变更审批边界

以下变化必须暂停当前任务并重新阅读 ACS 原始交付手册：

- 修改 Activity / Resolver / Snapshot 事实语义。
- 新增、删除或重命名公开 pywebview API。
- 改变记录中心指标序列或 PB 计算口径。
- 让前端根据原始数据自行补算事实。
- 将地图、照片、AI 生成提前纳入启动或总览阻塞链路。
- 引入需要用户产品选择的后台预取优先级或数据保留策略。
