# 百锐腾骑行复盘分析卡片缺失修复任务清单

本文档把 2026-08-06 对百锐腾骑行 FIT「功率/心率/踏频泳道已出现，但多个分析卡片仍无结果」的根因诊断，拆分为可独立执行、验证和交付的修复任务。

本轮问题的核心不是前端泳道渲染失败，而是后端把「缺失速度」误表达为「速度为 0」，下游骑行卡片又把速度 0 当成真实停顿，从而把功率、心率、踏频样本过滤为空。

本文是修复清单，不代表已经修复。后续执行时必须先完成失败基线和契约冻结，再改业务代码。

关键代码路径：

- `main.py`：`_build_fatigue_review_curve_bundle()` 使用 `float(r.get("speed") or 0.0)`，把缺失速度零填充。

- `main.py`：`_build_fatigue_review_curves_snapshot()` 将零填充速度曲线继续透传给前端和卡片信号。

## 1. 总体修复契约

所有任务必须遵守以下约束：

1. 前端只消费后端事实和后端结论，不从 DOM、ECharts、泳道曲线或截图推导分析结果。
2. 不做百锐腾设备特例；修复必须面向所有「FIT 缺失原生速度但存在距离/时间/功率/心率/踏频」的活动。
3. `missing speed`、`observed zero speed`、`derived speed` 是三种不同语义，不得混淆。
4. 缺失速度不得零填充为真实停顿证据。
5. 若使用 `distance/time` 推导速度，必须携带来源和质量标记；低质量推导不得输出过强结论。
6. 骑行卡片可以过滤真实滑行、停顿、异常功率和异常心率，但不能把缺失速度当成停顿。
7. 修复不能让无 GPS、无距离、无时间轴的活动伪装成完整速度分析。
8. 功率、心率、踏频样本不足时仍必须诚实返回 `unavailable / partial`，不得为了出结果而降低质量门槛。
9. 坡度曲线必须对重复距离、近零距离差和异常海拔跳变做保护，不能产生百万级坡度进入地形/疲劳判断。
10. 每个任务必须有自动化测试或真实样本回放证据。
11. 不顺手修改 ACS、AI prompt、LLM、打包、同步、标题、地图视觉或无关 UI。

# Phase B：速度缺失语义修复

## `BRY-FR-01`：禁止缺失速度零填充，建立速度来源和质量标记

优先级：P0  
性质：后端事实契约 / FIT 派生数据  
状态：已完成（2026-08-06）

目标文件：

- `fit_engine.py`
- `main.py`
- `metrics_resolver.py`（仅当速度/坡度派生逻辑在 Resolver 内部）
- `docs/js_api_contract.json`
- `tests/test_bryton_cycling_no_speed_review.py`
- 相关既有复盘测试

### 根因

`_build_fatigue_review_curve_bundle()` 使用 `float(r.get("speed") or 0.0)`，把「缺失速度」变成了「速度为 0」。后续所有使用速度判断停顿的逻辑都会把整条活动视为停顿。

### 必做

- 修改曲线构建：
  - 原始速度缺失时保留 `None` 或使用显式 missing 表达，不得直接变成 `0.0`。
  - 区分真实观测到的 `speed = 0` 和字段缺失。
- 增加速度来源/质量摘要：
  - observed speed 点数。
  - derived speed 点数。
  - missing speed 点数。
  - `speed_source` 与 `speed_data_quality`。
- 若距离和时间轴质量足够，使用 `distance/time` 推导骑行速度：
  - 只在 `distance` 单调、时间递增、间隔合理时推导。
  - 对重复距离、时间倒退、超长间隔、异常跳点返回 missing 或低置信，不输出虚假速度。
  - 推导速度不得覆盖原生观测速度；原生速度优先。
- 若距离/时间不足以推导速度，返回 `speed_source=missing`，下游不得视为停顿。

### 验收

- 对 no-speed 但有距离/时间的骑行 fixture：
  - `curves.speed` 不再是全 0 权威曲线。
  - `summary.speed_source` 或等价字段能说明速度来自推导或缺失。
  - `summary.speed_data_quality` 或等价字段不是把缺失伪装为 available observed。
- 对真实观测速度为 0 的 fixture：
  - 停顿仍能被识别为 stopped。
- 对无距离/无时间轴 fixture：
  - 不推导速度，不输出完整速度结论。

# Phase C：骑行卡片有效样本过滤修复

## `BRY-FR-02`：卡片过滤从“速度曲线存在”改为“速度事实可信”

优先级：P0  
性质：骑行复盘分析卡片 / 有效样本门控  
状态：已完成（2026-08-06）

目标文件：

- `main.py`
- `tests/test_bryton_cycling_no_speed_review.py`
- `tests/test_cycling_fatigue_review_metrics.py`
- `tests/test_cycling_fatigue_review_acceptance.py`

### 根因

骑行有氧漂移、有效踩踏功率保持、踏频节奏、心率漂移等卡片只检查 `speed_curve` 是否存在，然后用 `speed <= 1.0` 判停顿。全 0 速度曲线存在时，全部有效样本被过滤为 `stopped`。

### 必做

- 为卡片过滤提供速度可信度输入：
  - `speed_observed` 或 `speed_derived` 且质量足够时，才允许用速度过滤停顿。
  - `speed_missing` 时，不得使用 `speed <= 1.0` 作为停顿依据。
- 心率漂移：
  - 不再仅因速度缺失生成 `records<20`。
  - 若速度可推导，使用可信派生速度过滤。
  - 若速度不可用，但距离/时间/功率/踏频足以证明活动进行中，应返回更准确的 unavailable/partial reason，例如 `speed_missing`、`insufficient_aligned_hr_power_points`，而不是把全部样本当停顿。
- 有氧漂移：
  - 保持功率阈值、异常心率、时间间隔过滤。
  - 仅在速度可信时应用 stopped 过滤。
  - evidence 中保留过滤原因计数，便于排查。
- 有效踩踏功率保持：
  - 保持滑行/低功率过滤。
  - 速度缺失时不能让 `effective_power_points_count=0`。
  - 若有效功率点仍不足，原因应是 `coasting` 或 `insufficient_effective_pedaling_points`，不是伪 `stopped`。
- 踏频节奏：
  - 保持零踏频和低功率滑行过滤。
  - 速度缺失时不能把全部踏频正值过滤为 `stopped`。

### 验收

- no-speed 骑行 fixture 中：
  - `power_retention_signal.evidence.effective_power_points_count > 0`，除非功率本身确实不足。
  - `cadence_signal.evidence.effective_cadence_points_count > 0`，除非踏频本身确实不足。
  - `aerobic_drift_signal` 不再因为全量 stopped 变成 0 有效样本。
  - `filter_reasons` 不应在速度缺失场景出现全量 `stopped`。
- 真实停顿 fixture 中：
  - `stopped` 过滤仍生效。
- 滑行很多 fixture 中：
  - 低功率/零踏频仍不会被误判成有效踩踏。

# Phase D：坡度与地形派生保护

## `BRY-FR-03`：修复重复距离/近零距离差导致的极端坡度

优先级：P1  
性质：派生曲线稳定性 / 疲劳区间和事件辅助信号  
状态：已完成（2026-08-06）

目标文件：

- `metrics_resolver.py`
- `main.py`（仅当 grade/terrain_load 保护在快照层）
- `tests/test_bryton_cycling_no_speed_review.py`
- `tests/test_fatigue_zones_resolver.py`
- `tests/test_fatigue_review_bonk_risk_resolver.py`

### 根因

当前百锐腾样本的 `curves.grade` 出现百万级异常值，复现范围约 `-12571652.86` 到 `5088985.1`。这通常来自重复距离、近零距离差或异常海拔差导致坡度分母接近 0。

### 必做

- 对坡度计算增加距离差下限：
  - `delta_distance_m` 小于合理阈值时跳过、继承平滑值或标记 unavailable。
  - 不允许近零分母放大出百万级坡度。
- 对坡度输出增加物理合理边界：
  - 超出合理骑行/跑步范围的点进入异常过滤，不进入 `terrain_load` 或疲劳事件判断。
  - 保留缺失/异常计数到 debug/evidence，不暴露原始 records。
- 确认 `terrain_load` 不因缺失速度或异常坡度输出虚假强地形负荷。
