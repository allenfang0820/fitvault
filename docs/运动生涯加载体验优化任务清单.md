# 运动生涯加载体验优化任务清单

本文档用于指导「运动生涯」页面从当前“进入后一次性加载多模块数据”优化为“首屏优先、子页按需、后台预取、缓存可用”的加载模式。

当前确认的基线：

- 应用启动默认打开「个人运动数据」，首访说明场景打开「帮助说明」。
- 只有切入一级导航「运动生涯」时，才触发 `loadCareerData()`。
- 当前 `loadCareerData()` 会在进入运动生涯后统一触发总览、年度、时间轴、赛事档案、记录中心、足迹、相册等加载。
- 已存在 `get_career_overview_secondary_metrics` 这种“总览首屏先返回、次级指标延后合并”的局部优化模式，本次优化应复用这个方向。

## 0. 总原则

1. 首屏优先：进入「运动生涯」后，优先渲染总览骨架和关键事实。
2. 按需加载：用户未进入的子页不应阻塞首屏。
3. 后台预取：总览稳定后，可预取最可能访问的子模块，但不能影响首屏响应。
4. 陈旧可用：已有缓存可先展示，再静默刷新最新数据。
5. 独立失败：一个子模块加载失败，不应让整个运动生涯页面进入失败态。
6. 前端只消费后端事实，不新增赛事、PB、成就、运动类型、足迹等事实判断逻辑。
7. 不改变数据库事实模型，不重写 Resolver，不改变 Activity 单一事实源原则。

## 1. 非目标

- 不重做运动生涯视觉设计。
- 不新增真实 AI 调用。
- 不修改 PB、赛事、成就、足迹、相册的业务判定规则。
- 不改变 pywebview API 的既有字段语义；如需新增状态字段，必须同步契约和测试。
- 不为加载体验引入本地伪数据或前端推断数据。
- 不在应用启动时全量预热运动生涯数据。

## 2. 目标加载模型

推荐目标模型：

```text
进入运动生涯
  -> 立即渲染页面壳、总览骨架、已有缓存
  -> 拉取 get_career_overview
  -> 渲染总览关键事实
  -> 后台拉取 overview secondary metrics
  -> 空闲时预取 timeline / records center 的轻量入口数据
  -> 用户进入具体子页时再加载对应完整数据
```

优先预取顺序：

1. 时间轴：用户从总览进入下一层的概率高。
2. 记录中心：数据较重但价值高，应支持轻量入口和完整分析分离。
3. 赛事档案：可在用户进入子页或点击赛事入口后加载。
4. 足迹 / 相册：地图脚本和图片预览更重，应延后到子页可见后加载。
5. 年度 AI 总结：默认只读预热，用户进入「AI 总结」时优先命中缓存，不触发生成。

## 3. 正式执行顺序

### `CAREER-LOAD-00`：刷新加载链路基线

目标：在动代码前确认当前真实调用链，避免基于过期实现改造。

必须检查：

- `switchTab()` 中 `activePanel === 'career'` 的调用路径。
- `loadCareerData()` 内部触发的所有子加载。
- `switchCareerPage()` 对 `pb`、`insight`、`footprint` 的额外触发。
- `invalidateCareerDataCaches()` 与 `careerSourceVersion` 的刷新行为。
- 现有测试中对“一进入 career 就加载所有模块”的断言。

验收：

- 形成当前调用链摘录，明确哪些测试需要随加载模式同步调整。
- 不改业务代码。

### `CAREER-LOAD-01`：拆分 `loadCareerData()` 为首屏加载与子模块加载

目标：`loadCareerData()` 不再阻塞等待所有子模块。

建议实现：

- 保留 `loadCareerData()` 作为进入运动生涯的总入口。
- 新增或重组内部函数：
  - `loadCareerFirstPaint()`
  - `loadCareerOverviewBundle()`
  - `scheduleCareerBackgroundPrefetch()`
  - `loadCareerPageData(page, options)`
- 首屏只等待 `loadCareerOverview()` 和必要的 `loadCareerSeasons()` 轻量数据。
- 时间轴、赛事档案、记录中心、足迹、相册不再作为首屏必需项。

验收：

- 切入运动生涯后，总览可以在子模块未完成时渲染。
- 任一子模块失败不会设置全局 `careerDataNeedsRefresh` 使总览反复重载。
- 旧的重复并发保护 `careerDataLoadingPromise` 仍然有效。

### `CAREER-LOAD-02`：建立子页按需加载状态

目标：每个子页有独立 loaded / loading / error / sourceVersion 状态。

建议状态结构：

```text
appState.career.pageLoadState = {
  overview: { loaded, loadingPromise, error, sourceVersion },
  timeline: { loaded, loadingPromise, error, sourceVersion },
  races: { loaded, loadingPromise, error, sourceVersion },
  pb: { loaded, loadingPromise, error, sourceVersion },
  footprint: { loaded, loadingPromise, error, sourceVersion },
  memory: { loaded, loadingPromise, error, sourceVersion },
  insight: { loaded, loadingPromise, error, sourceVersion }
}
```

边界：

- 可以使用更贴合现有代码的命名，但必须表达同等语义。
- 不要求一次性重构所有缓存结构；允许兼容现有 `appState.career.*LoadingPromise`。

验收：

- 切到「时间轴」只加载时间轴所需数据。
- 切到「赛事档案」只加载赛事档案所需数据。
- 切到「记录」加载记录中心，且不强制刷新已经可用的同版本缓存。
- 切到「足迹」时才加载地图脚本或重绘地图。

### `CAREER-LOAD-03`：实现后台预取策略

目标：总览首屏完成后，温和预取高概率子页数据，减少下一跳等待。

建议实现：

- 总览渲染完成后，用 `requestIdleCallback` 或 `setTimeout` 调度预取。
- 优先预取 `timeline` 的默认筛选数据。
- 预取 `pb` 时只拉目录和当前记录，不立即拉所有指标分析曲线。
- 预取必须可取消或可被同版本缓存复用，不能与用户切页触发的加载互相打架。

边界：

- 不预取足迹地图脚本。
- 不预取相册图片预览大图。
- 不触发年度 AI 总结生成。
- 不在启动 App 时预取运动生涯。

验收：

- 首屏 API 调用数量减少。
- 用户进入时间轴或记录中心时，已有预取数据可直接复用。
- 预取失败只记录子模块错误，不影响总览。

### `CAREER-LOAD-03A`：年度 AI 总结只读预热

目标：在进入运动生涯后，后台空闲时先预热年度 AI 总结的只读接口结果，缩短首次进入「AI 总结」的等待感。

建议实现：

- 仅预热 `get_career_year_insight`，不触发 `generate_career_year_insight`。
- 预热只做缓存填充，不主动切换页面、不展示生成态。
- 用户真正进入「AI 总结」后，优先复用同版本缓存。
- 若预热尚未完成，前台进入页不重复发起同类只读请求。

边界：

- 不改变年度总结生成逻辑。
- 不扩大到历史年度批量预热。
- 不引入任何前端推断或虚构总结内容。

验收：

- 首次进入「AI 总结」时，若后台预热已完成，可直接展示缓存。
- 预热进行中时，前台进入页不会叠加重复请求。
- 预热失败只影响该子页缓存，不影响总览与其他子页。

### `CAREER-LOAD-04`：改造记录中心重数据加载

目标：记录中心支持“入口数据”和“分析数据”分层。

建议实现：

- `get_career_record_catalog` 与 `get_career_records` 可作为记录中心首屏数据。
- `get_career_record_detail` 与 `get_career_record_metric_series` 只在选中记录后加载。
- 切换运动类型时优先复用 `recordsBySport` 同版本缓存。

验收：

- 进入运动生涯总览不会触发记录中心全部分析曲线。
- 进入记录中心后，左侧列表先可见，右侧分析按选中项加载。
- 切换记录指标不触发全量运动生涯刷新。

### `CAREER-LOAD-05`：陈旧可用与刷新提示

目标：已有缓存先展示，后台刷新后再合并，避免用户看到空白等待。

建议实现：

- 使用 `careerSourceVersion` 判断缓存是否同源。
- 同源缓存直接渲染。
- 数据源变化后标记对应子页 stale，并在后台刷新。
- 刷新时在子模块区域显示轻量刷新状态，不覆盖已有内容。

验收：

- 用户重复进入运动生涯时，已有总览立即显示。
- 导入 FIT、删除活动、切换赛事标记后，相关子页会刷新，但未受影响子页不强制清空。
- 刷新失败保留旧内容，并给出产品化错误状态。

### `CAREER-LOAD-06`：测试与契约同步

目标：把加载边界固化成测试，防止未来又回到一口气全量加载。

必须补充或调整：

- 前端静态测试：`switchTab('career')` 只要求首屏加载，不要求所有子模块同步完成。
- 前端静态测试：`switchCareerPage('timeline')` 触发时间轴加载。
- 前端静态测试：`switchCareerPage('races')` 触发赛事档案加载。
- 前端静态测试：`switchCareerPage('pb')` 触发记录中心入口加载，但不强制全部分析曲线。
- 失败隔离测试：时间轴失败不影响总览 loaded 状态。
- 契约检查：如新增 API 字段或状态枚举，更新 `docs/js_api_contract.json`。

建议运行：

```bash
.venv312/bin/python -m pytest \
  tests/test_career_overview_frontend_render.py \
  tests/test_career_timeline_frontend_render.py \
  tests/test_career_archives_frontend_render.py \
  tests/test_career_footprint_frontend.py \
  tests/test_career_memory_frontend_render.py \
  tests/test_career_p0_product_shell.py

git diff --check
```

验收：

- 聚焦测试通过。
- `git diff --check` 通过。
- 如全量生涯测试仍存在既有基线失败，必须单独列出，不混入本任务结论。

## 4. 验收口径

完成本优化后，用户体验应满足：

- 首次点击「运动生涯」时，用户先看到总览内容，而不是等待所有子页完成。
- 用户未打开的重模块不阻塞当前页面。
- 切换到子页时，有局部加载和局部错误状态。
- 重复进入页面时，旧数据可立即显示，后台刷新不造成闪屏。
- 数据事实仍以后端为准，前端只负责加载编排和展示。

## 5. 风险提示

- 当前测试可能把旧加载模式写成了断言，改造时需要先判断测试是在保护契约，还是只是保护旧实现细节。
- `loadCareerData()` 现在兼具“进入生涯入口”和“全量刷新”职责，拆分时要避免造成缓存失效和重复请求。
- 记录中心、足迹、相册可能有图表或地图可见性依赖，按需加载时要同步处理 resize / rerender。
- 后台预取不能吞掉用户主动切页的错误提示，用户当前可见页面的加载状态优先级最高。
